# GeoMapKit: architecture (first draft)

Status: draft from the first design discussion, 2026-11-06. Nothing is built or verified. Background on frameworks, data sets and licences is in `maps-summary.md` (TrainingApp repo, `docs/design/`); those facts come from memory and need checking.

## 1. Goals

- A mapping kit for iOS, iPadOS, macOS and watchOS, used first for trail running (also walking and cycling).
- Combine data from several sources into tiles, render them with our own renderer, and route with our own router.
- Offline first. Small areas (a valley, a city), not whole countries.
- Pure Swift in the core targets so everything builds for watchOS.

### Battery (watchOS first, not a concern on macOS)

A cross-cutting constraint. A trail run can last hours with GPS, heart rate and the display all active, so the map must add as little as possible. Principles:

- **Draw only when something changed.** Redraw on a new position fix, a Crown turn or a screen wake, never on a timer. No continuous animation.
- **Always-on display:** a reduced, static view (route, position, no animation), redrawn at most about once per second, or per the system's cadence.
- **Cache the rendered view** and move it for small position changes; rebuild only when the position leaves the cached area or the zoom changes.
- **Precompute on the phone,** never on the Watch: simplification per zoom, the corridor graph, the feature cells. The Watch only reads.
- **Memory-mapped, read-only data** with no decode-everything step, so wake-ups stay cheap.
- **Reroute on the Watch is rare and bounded:** it runs only when the phone is out of reach and the runner is off route, on the small corridor graph, with an iteration cap.
- **Location updates and sensors belong to the app's workout session,** not to the map; the kit takes positions as input and does not start its own location updates.
- **Measure:** an energy budget per feature (Instruments Energy Log on a real Watch) is part of definition-of-done for the renderer and the follower.

## 2. Decisions so far

| Topic | Decision |
|---|---|
| Renderer | Own renderer. Core Graphics / SwiftUI `Canvas` backend first, behind a `MapRenderer` protocol. A Metal backend on iOS only if profiling shows a need. |
| Router | Own router. One implementation (A*) for phone and Watch. |
| Map data format | **Own feature store, no MVT and no PMTiles.** All map data comes from our own OSM processing; outside tile sources are not a requirement. Parsed OSM features are stored in a compact format of our own, grouped spatially (by z/x/y or a similar grid) so a Watch corridor can still be cut by region and the renderer loads only what is on screen. |
| Planning | On iPhone, iPad or Mac, on a regional graph for a small downloaded area. |
| Watch | Receives the route, a corridor graph and corridor tiles. It follows the route and only reroutes when the phone is out of reach. |
| Rejoin | After leaving the route, reroute to the best nearby route point, not necessarily back to the exit point (section 6). |
| Route types (v3) | A to B with via-points, out-and-back, and import of a GPX track with map-matching to the graph. No loop generation in v1, but `Router` stays usable by a future loop generator. |
| Activities (v3, routing) | Running and walking (one profile family). Cycling is not in v1, but its edge attributes (one-way, `bicycle` access, `mtb:scale`) are stored in the graph from the start so graphs need no rebuild later. |
| Waypoints | Waypoints carry a `required` flag. A rejoin cannot skip past the next unreached required waypoint. Via-points placed while planning are required by default; optional points of interest are not. |
| Pipeline | Graph building happens **on device**, in Swift, in the package (OSM data for a user-chosen area in, routing graph out). Pre-built server files are not the v1 path. |
| OSM input | OSM data comes as **PBF** (`.osm.pbf`) from the start, read by a Swift PBF reader in the package (`OSMPBF` target). Overpass is not used. The reader sits behind an `OSMDataSource` protocol so the origin of the bytes (bundled file, download, our own host) can change. |
| PBF sourcing | Phase 1: a **test Mac app** that uses the package and downloads full regional PBF files (for example from Geofabrik), cuts the chosen area and builds graph and map data. Phase 2: smaller area PBFs hosted on a server of ours, downloaded by the apps. The area-cutting code lives in the package, so the same code later produces the hosted files. |
| Elevation (v1) | No DEM in v1. The cost model uses tags only (surface, `sac_scale`, road class). The graph format reserves optional ascent/descent fields so a DEM step can be added later without a format break. The Watch barometer remains the source for recorded elevation. |
| Distribution | The kit will be distributed at some point, so licence, attribution and data-source terms are release gates (section 9). |
| Release plan (provisional) | **v1 is map rendering only, on all platforms.** v1: PBF reader, area cutting, lossless feature store, style and labels, the renderer on iOS, iPadOS, macOS and watchOS, a map view with pan and zoom, and delivery of a map region to the Watch (a region cut on the phone or Mac, with no track involved). **Not in v1:** tracks, GPX, route following, track-based corridors and routing. **v2:** tracks (GPX import, a `Route` model, overlay, `RouteFollower`, corridor cut from a track). **v3:** routing (graph builder, router and cost model, route planning, map-matching, rejoin rerouting). The track and routing decisions in this document are the design for those later steps. |
| Off-trail (v2, provisional) | A track created beforehand (for example on the Mac) may go off-trail, and the app must follow it. Orienteering itself is not a use case: routing and tracks are not allowed in competition, so there is no orienteering mode, no ordered controls and no punching. Nothing in v1 may assume that a route lies on paths. A route is an ordered polyline with waypoints, and each leg can be a free leg (straight or free-form, not on any path) or, in v2, a leg on the path network. `RouteFollower` works on any polyline without a graph. Off-route detection on a free leg uses the same rules as on any track. The Watch corridor stays a ribbon around the track. Terrain-cost routing across land cover is not planned (question 41). |
| Cost model (v3) | A `CostProfile` is a table of weights (data, not code), chosen by user preference. Presets: trail running, road running, walking. Adjusted by a few user settings: road avoidance, surface preference and a maximum difficulty (`sac_scale` limit). `mountain_hiking` is acceptable when the user allows it; the limit is a user setting, not a fixed exclusion. Default limit: up to `mountain_hiking` (to confirm). Missing tags default to a mid value, never to the easiest. A full per-surface weight editor is deferred; the data-table design allows it later without a router change. The A* heuristic is computed from the fastest speed of the profile in use, so it stays admissible. |
| Platforms | Minimum version 26 on all platforms: iOS, iPadOS, macOS and watchOS. No availability checks for older systems. |
| Language | Swift 6 language mode with strict concurrency from the start. Value types and `Sendable` by default; explicit isolation (actors) for caches and file readers. |
| Numeric types and geometry conventions | `Int` may be 32 bits on some Watch hardware (to verify), so OSM IDs and file offsets use explicit `Int64`/`UInt64`. `TileID.maximumZoom` is 30 so `1 << zoom` is safe there. Longitude +180 is treated as -180 (column 0); bounding boxes crossing or ending at the antimeridian are not supported. Computed tile corners are not used to identify a tile (floating-point rounding); use a point inside it. Decoded tile IDs are validated, since they arrive from manifests and Watch requests. |
| Extract representation | An `OSMExtract` stores nodes, ways and relations in columns (IDs, coordinates as 32-bit integers in 1e-7 degrees, flat vertex and member arrays) with tags as ranges of key and value IDs into one shared table of distinct strings. Strings are interned **byte for byte**, not with Swift `String` equality, which treats canonically equivalent strings (for example a precomposed and a decomposed "é") as equal and would silently merge different data; the reader keeps tags as an ordered list of `OSMTag` for the same reason (question 46). Tags are kept in key order so output is deterministic. Elements (`OSMNode`, `OSMWay`, `ExtractedRelation`) are built on demand; accessors read the columns without allocating. Oslo, 15 km: the extract's data is 164 MB in columns (`OSMExtract.memoryBytes`, stable); the process footprint with the extract alive was 860 to 930 MB as dictionaries and 220 to 440 MB compact over several runs (the figure varies with how much freed memory the allocator has not yet returned, so `memoryBytes` is the reliable number); the cut's peak heap fell from 899 MB to about 445 MB. Verified by a content digest identical to the dictionary version on Liechtenstein and Oslo. |
| Feature store file format v1 | Implemented in `FeatureStore` (`FeatureStoreWriter`, `FeatureStoreFile`). Little-endian; a 144-byte header (magic `GMKM`, format version, classifier version, storage zoom, band mask, cell count, bounding box and source date, file length, six section ranges) and a CRC-32 in the last four bytes. Sections: cell index (24-byte entries `x, y, offset, length`, sorted by `(x, y)`, binary search), cell blocks, string offsets, string bytes, relation table (sorted by ID, binary search), attribution. A cell block stores its own origin (not derived from the tile, so files from other platforms agree) and three band bodies; a band groups features by class, so a hidden class is skipped by its byte length. Features carry object type and ID, piece flags (`continuesBefore`, `continuesAfter`, `incomplete`), subclass, name ID, offset along the line in cm, tags (**detail band only**) and parts of vertices delta-coded as zigzag varints in 1e-7 degrees, with artificial-edge runs. The string table is byte-exact and renumbered by use count (most used string = ID 0). Opening checks only header and section ranges (cheap, for the Watch); lookups validate what they touch; `verify()` checks the CRC and the whole structure and runs after a transfer. Every read is bounds-checked and counts are capped by the remaining bytes. Output is deterministic. Decided with this: `FeatureStore` holds format and reader (Watch-safe); the builder will be a separate target `FeatureStoreBuilder` that depends on `OSMPBF`, so the Watch does not link the PBF and Compression code. Incomplete multipolygons are outline-only as a whole (all or nothing). Route-relation assembled lines are deferred. Question 46 (ordered byte-exact tags) is resolved. For question 45 the recommendation is one store file per block (for example a z9 or z10 tile) plus a manifest, with a reader that routes by cell, so no merge step is needed. |
| Own coordinate types | `GeoCore` uses its own `Coordinate` (and later its own live-position type for `RouteFollower`), not `CLLocationCoordinate2D` or `CLLocation`, so the core stays free of Apple frameworks (hosted area files may be produced on Linux) and the type is `Hashable`, `Codable` and under our control. Conversions to and from CoreLocation types live in a small adapter wrapped in `#if canImport(CoreLocation)`. `Coordinate` is immutable and its initializer does not validate (no failable init at every call site); consumers handle bad values, and `isValid` is available where strictness is needed, for example when reading untrusted files. |
| Overlays (v2) | A generic `MapOverlay` protocol (points, lines, polygons with a style). Only GPX tracks in v1 (the planned route and the current track). The kit knows nothing about Strava or HealthKit. |

## 4. Data products

From the same OSM source (plus DEM and land cover) the pipeline makes two products:

1. **Render features:** our own feature store, spatially grouped, with per-zoom simplification baked in. (Contours and hillshade are out of v1 because there is no DEM.)
2. **Routing graph:** a compact binary file. Nodes at junctions, edges with length, surface, `sac_scale`, access and ascent/descent from the DEM. Memory-mapped, fixed-width arrays (CSR adjacency), versioned.

Rendered tiles are generalized and clipped, so they cannot be used for routing.

### Feature store layout (decided)

- **Cells:** the standard z/x/y Web Mercator grid at one fixed storage zoom (z13, decided). The index is a sorted, memory-mapped array of `(x, y) -> offset, length`.
- **Bands:** simplified geometry is baked in per zoom band (starting guess: overview z8 to 11, mid z12 to 14, detail z15 and up). The Watch never simplifies. Every feature has a minimum band, so the reader can skip it without decoding.
- **Geometry:** integer coordinates in OSM's native 1e-7 degree units, relative to the cell origin, delta-coded as varints. This is lossless against the OSM source (a coarser grid would quantize it). Simplified bands are extra copies; the detail band is the original geometry.
- **Clipping:** lines and polygons are clipped at cell edges. Every feature has a stable ID (OSM way or relation ID). Each clipped piece carries the ID, `continuesBefore`/`continuesAfter` flags, and its offset along the line (measured along the geometry of the band that is drawn, which is the original line in the detail band), so the renderer can join pieces, keep dash patterns continuous, draw one label per feature and hit-test whole features. Polygon edges that lie on a cell border are marked artificial, so they are filled but not stroked.
- **No loss of OSM data on macOS and iOS (decided):** the store keeps the same feature granularity as OSM. Every feature (node, way, relation as modelled) is stored with **all of its tags**. A shared dictionary of keys and values and a per-feature list of dictionary indices keep this compact without losing anything. The builder additionally derives a compact **feature class** plus flags for rendering; the class is derived data and never replaces the tags, and features the classifier does not recognize are kept with class `other`. The renderer and style work on classes; everything else (search, inspection, the graph builder, future styling) can read the raw tags. A shared string table holds names and other values.
- **Two files plus a manifest:** `map` (features) and `graph` (routing), with a shared header, version and bounding box. Map features and graph edges share the OSM way ID.
- **Layer profile:** which classes show at which band is a user setting on macOS and iOS (class to lowest visible band, or hidden), applied when reading, so a change needs no rebuild. The Watch has no setting: the phone applies the profile when it cuts the corridor and drops hidden features from the Watch copy. A profile change reaches the Watch with the next corridor.
- **Watch shows less than iOS (decided):** for the same workout and scale, the Watch map shows only the **essential minimum**: what a runner needs while running (the route, the runner's position and the trail or path they are on, with a few anchors such as junctions, water and major roads where useful). Everything else is left to the iPhone: when the runner is lost or wants detail, they use the phone. The Watch feature set is therefore a smaller, fixed profile applied when the corridor is cut, not the user's iOS layer profile. Exception: if the runner has only the Watch with them (no phone), the Watch may need a richer set (for example more path context for navigating when lost). Open: how the Watch knows it is phone-less (phone not reachable) and whether it then switches to a richer profile, which would require the richer features to be present in the corridor already (see question 37).
- **Relations (decided):** all relation types are stored losslessly, as tags plus an ordered member list with roles (member type, ID and role), whatever the type. In addition, the builder derives **assembled geometry** where it helps drawing: multipolygons are assembled into area features with holes (outer and inner rings joined from member ways), and hiking/running route relations get an optional assembled line for drawing and labelling. Assembled geometry is derived data and never replaces the membership list. Relations spanning several cells are stored once, with the member IDs resolvable across cells.
- **Areas that span cells or the extract (decided):**
  - Clipping happens on the **complete assembled polygon**, never on a partial one. Edges that the clip creates along a cell border are marked artificial; the renderer fills the clipped ring and strokes only real edges. Neighbouring cells hold their own piece of the same area and meet at the border, so the area looks continuous. Draw fills without an anti-aliased outline (or with a tiny overlap) to avoid hairline seams between cells.
  - The area cut (see question 31) **completes relations that touch the box**: all member ways of a touching relation are kept whole with their nodes, so multipolygons can be assembled. Completion has a size limit; relations above it are marked incomplete.
  - An area that still cannot be assembled gets an `incomplete` flag and keeps its membership list. The renderer draws the known outline as a line and does not fill it; it never guesses the inside from an open ring.
- **Watch zoom limits and ultras (proposed numbers):** live view zooms out to about 30 km across and in to about 100 m across, with the basemap drawn inside the corridor only. Ultra marathons (50 to 170 km and longer, 10 to 40 hours) are in scope. For a whole-route overview, which may span 100 km or more, the Watch draws a simplified route line plus waypoints (aid stations, the runner's position, remaining distance) and no basemap features, as a separate mode. This needs no overview band. Ultras make these points matter more: very tight battery over 24 hours or more, long corridors (question 39), phone-less runs (question 37), required waypoints at aid stations and checkpoints, GPX import as a main use case, and routes that cross themselves, which makes progress-along-route tracking essential.
- **Ultra hardware assumption (to verify):** ultra runs are assumed to use an Apple Watch Ultra with the maximum battery-saving workout mode. The specs of the newest model are unconfirmed. The principles stay the same on every Watch. Consequence for the kit: do not assume a position fix every second. In power-saving modes GPS and heart rate are sampled less often, so `RouteFollower` thresholds (off-route distance, hysteresis, rejoin tolerance) depend on the observed fix interval and speed, which are inputs; positions between fixes are interpolated along the route; live snapping reports a confidence and does not jump between passes on loops and self-crossings. Tests must include sparse tracks.
- **Watch zoom range (decided):** on the Watch the user does not zoom out further than tens of kilometres for running, or hundreds of kilometres for cycling. The corridor therefore does not need the overview band for running. Overview geometry stays an iOS/macOS concern. A zoomed-out Watch view shows the route and the corridor ribbon around it, and there is no basemap outside the corridor to draw. Cycling is not a Watch map use case (decided): a Watch is not usable as a map while cycling, and cyclists use an iPhone on a handlebar mount. So there is no cycling corridor strategy or coarser Watch band; the Watch map is for running and walking. Cycling is served by the iPhone (and iPad/Mac), which has the full regional graph and all bands. Cycling edge attributes are still stored in the graph (see Activities).
- **Watch map data requests (decided):** the Watch requests map data from the iPhone whenever the map is used and the Watch does not have data for the area on screen. The phone does all the cutting; the Watch only asks for an area (a set of z13 cells) and stores what it receives. The phone supports **predownloading of areas**, so the data is normally already on the phone when the Watch asks. Triggers: (1) when a run is started, or when the map app is started on the Watch, it requests an area around the current location, or, once tracks exist (v2), around the track; (2) afterwards new data is requested only when the runner leaves the held area, which should be very rare. Assumption for a run without a track: the distance is under 25 km and probably a round trip, so a **15 km radius around the start** is enough; leaving it is expected at most once per run, if at all. Very long runs are the exception, and they will normally have a track. If the phone is unreachable when the runner leaves the area, the Watch keeps drawing what it has and the runner's own trail, with a notice that the map has ended. Cells are sent nearest-first so the map appears quickly.
- **Classes are not a filter at build time:** because nothing is dropped, the earlier idea of core and optional classes chosen when an area is built is superseded (reinstate it only if area size turns out to be a problem). What is shown is decided by the layer profile (iOS/macOS) or the fixed Watch profile (corridor cut), both working on derived classes.

### Feature classes (decided, `FeatureClassifier` rule table version 2)

An ordered rule table; the first match wins, so an object has one class, and the raw tags are always kept. Version 1 had 17 classes; **version 2** (question 47, plus power lines, ski pistes and lifts as navigation landmarks) appends classes 17 to 23, and the numbers of the existing classes did not change. Order: peak, place, anchors (`amenity` drinking water, shelter, toilets; `natural=spring`; `tourism` huts and viewpoint), highway, railway, power, aerialway, piste, waterway, water areas, forest, tree, boundary, land cover, urban land use, building, barrier, transport stop, road point, other POI keys, `other`. A `piste:type` way that is also a highway stays a path or track. Anchors come before `building`, so a hut tagged as a building is a hut. Nodes are points, open ways lines, assembled multipolygons areas. A closed way is an area if it has `area=yes`, or an area key (`building`, `landuse`, `leisure`, `amenity`, `tourism`, `shop`, `historic`, `aeroway`, `place`, most `natural` and `man_made` values, `waterway=riverbank`, `boundary=protected_area|national_park`), unless it also has `highway`, `railway` or `barrier` (then a line) or `area=no`. The subclass byte holds the specific value in its low six bits (the `highway` value, the `tracktype` grade for tracks, and so on), bit 6 for a bridge and bit 7 for a tunnel. A band is the lowest band a feature is stored in; it is also stored in the bands above it, so a mid-band feature is in mid and detail. Bands are fixed per rule, not by feature size.

### Clipping and simplification (decided, `FeatureStoreBuilder`)

- **Order:** a feature is simplified per band as a whole, then clipped to cells; the detail band is never simplified.
- **Space:** intersections are computed in Web Mercator in `Double` (x is longitude in 1e-7 degrees, y the projected latitude), because a segment is straight on the screen in Mercator and not in latitude/longitude. Only the final vertices are rounded to 1e-7 degrees.
- **Cell borders** are integers in 1e-7 degrees from one rounding function, so two neighbours share the same integer. A cell is closed: a vertex exactly on a border belongs to both cells.
- **Seams:** a border point is computed from the original segment and the border with the segment's end points in a fixed order, so both neighbours get the same point, apart from a rare rounding tie of one unit (1e-7 degrees, about 1 cm). The tests allow one unit.
- **Lines:** clipped per segment (Liang–Barsky). A line that leaves and re-enters gives several pieces, each with its own offset. `continuesBefore` and `continuesAfter` are set when the piece does not begin or end at the first or last vertex of the line. A piece that is a single point is dropped, and a piece lying along the east or south border belongs to the neighbouring cell. The offset is the cumulative haversine distance in centimetres to the piece's first vertex.
- **Rings:** Sutherland–Hodgman, with each edge tracked as real or artificial: the edge that joins a point where the ring leaves the cell to the next point where it returns is artificial; fragments of real edges stay real. A ring that covers the cell becomes the cell's square, all artificial. A result with zero area is dropped. Fill uses the even-odd rule, so a hole that covers the cell cancels the outer ring.
- **Simplification:** Douglas–Peucker in Web Mercator; tolerance 0.5 pixel of a 256-pixel tile at the highest zoom of the band (about 38 m for overview at zoom 11 and 4.8 m for mid at zoom 14 at the equator, smaller on the ground at higher latitudes). End points are kept; a ring keeps at least three distinct vertices or is dropped from that band. Neighbouring polygons are simplified independently, so a shared border can open a small gap in the overview and mid bands, and a simplified ring can cross itself in rare cases. Measure on real data before adding shared-border simplification.
- **Not supported:** the antimeridian. **Cost:** every cell in a feature's bounding box is clipped separately, which is quadratic for very large polygons; measure on the end-to-end data and add a strip-wise pre-clip if needed.

### Multipolygon assembly (decided, `FeatureStoreBuilder`)

- **Scope:** only `type=multipolygon` relations are assembled. Boundary and route relations stay in the relation table only; assembled route lines are deferred.
- **Rings:** outer and inner way members are joined separately, end to end by shared node ID (ways reversed as needed; a closed way is a ring by itself). Role `outer` and an empty role are outer rings, `inner` is a hole, other roles and non-way members are ignored. Where several unused ways meet at a node the lowest way ID is taken, so the result does not depend on the order of the members; if that leaves a chain open, the relation is incomplete. Ways join by node ID, not by position, so two ways that end at different nodes with identical coordinates do not join.
- **Holes:** each inner ring goes to the smallest outer ring that contains most of a sample of its vertices (at most five, shared vertices ignored, and the bounding boxes must nest, so many holes in a large outer ring stay cheap). An island inside a hole is its own outer ring. Outer rings are normalized counter-clockwise and inner rings clockwise in Web Mercator; fill with the even-odd rule.
- **Incomplete (all or nothing):** a relation is incomplete if the extract flags it, a member way or node is missing, any ring does not close, or there is no usable outer ring. It then produces no polygon. Its rings and chains come out as **line features** (object type relation, the relation ID, class from the relation's tags, flag `incomplete`), clipped like lines with continuation flags and offsets; the renderer draws an outline and never fills.
- **Tags:** the classifier gets the relation's tags without `type`. Old style: if the relation has no tags besides `type` and exactly one outer way, the way's tags are used and that way is not emitted a second time. Untagged member ways are not emitted separately; their geometry is in the area and their IDs in the relation's member list. Tagged member ways are emitted normally.
- **Counted, not repaired:** an assembly report counts unclosed chains, rings without area or with fewer than four points, inner rings that no outer ring contains (ignored, the polygons stay valid), missing members and duplicate members. **Self-intersections are not detected** (a check is O(n^2) per ring, too slow for coastline-sized rings), so a self-intersecting ring is filled even-odd; this replaces the earlier idea that the report counts them.

### Store builder (decided, `FeatureStoreBuilder.build(from:)`)

- **Cells written:** only the cells that lie fully inside the extract's bounding box (a rectangle of columns and rows), because the extract is incomplete near its edge. Pieces that fall in other cells are dropped and counted (`piecesOutsideCells`). A box smaller than one cell gives an empty, valid store. The file's bounding box is that of the written cells. A cell owns its west and north border, not its east and south border, which also decides where a point or a piece lying along a border goes.
- **What is stored:** every tagged node as a point (untagged nodes only as way vertices), every way as a line or area with all its tags, every relation in the relation table (all types, tags and members, `isIncomplete` mirrors the extract's flag). A feature is stored in its lowest band and every band above it; tags only in the detail band, the `name` value in all bands. Untagged ways that are members of a multipolygon are not stored separately, and a single outer way whose tags a tag-less multipolygon adopts is not stored twice; untagged ways in no relation are stored as `other` lines. A way with a node missing from the extract is split at the gap (the pieces are counted in `waysWithMissingNodes`), never drawn across it. Consecutive duplicate vertices are merged.
- **Multipolygons:** assembled as described above; incomplete ones become line features of the relation's class with the `incomplete` flag (clipped as lines, with continuation flags and offsets).
- **Watch copy (`BuildProfile.watch`, provisional):** only classes with the Watch flag, bands mid and detail only, only the `name` tag, and no relation table. The writer drops strings that nothing uses, so the Watch copy carries a pruned string table. The corridor cut for the Watch may refine this.
- **Reporting:** `BuildReport` counts what was stored, suppressed and skipped; `FeatureStoreFile.statistics()` gives sizes and counts per band and class for measurements. Builds are deterministic.
- **Cost:** the whole result is held in memory (one writer per block of cells), single-threaded, with cancellation checks.
- **Measured on the real Liechtenstein extract** (Geofabrik, 2026-11-05, 3.50 MB, centre 47.14 N 9.52 E; release build on a Mac, one run each, warm file cache). 10 km radius: the cut gives 330,704 nodes, 38,335 ways and 954 relations (13.2 MB as an extract, cut 0.25 s). The **full store** takes 0.37 s to build and is 3.93 MB in 22 cells: overview 57 KB (1,012 features), mid 661 KB (12,732), detail 2,552 KB (48,869), about 52 bytes per feature in every band; string table 222 KB (11,121 strings), relation table 441 KB. That is 112 % of the compressed source file and 30 % of the extract's memory. The **Watch copy** takes 0.24 s and is 1.66 MB (47 % of the source): mid 599 KB (12,230 features), detail 1,050 KB (16,095), string table 15 KB. 15 km radius (this covers the whole country): 358,093 nodes, 42,120 ways, 1,030 relations; full store 5.04 MB in 41 cells, Watch copy 2.20 MB in 35 cells. Opening a file takes no measurable time, `verify()` 10 to 30 ms, and reading the busiest cell (8,813 detail features) takes 2.0 ms for the detail band and 0.3 to 0.5 ms for the mid band (0.5 ms for the Watch copy's detail band). The numbers answer question 36 for this region: a lossless store of a 15 km area is about 5 MB, and the Watch copy about 2 MB. Other regions are denser (Oslo has about 12 times the nodes), so repeat the measurement there before setting a Watch ceiling (question 39, 43).
- **Content checks on the same data** (`LiechtensteinEndToEndTests`, skipped unless `GEOMAPKIT_LIECHTENSTEIN_PBF` points to the file): every relation (tags, members, roles) and every tagged node is in the file byte for byte; for 31,215 ways the tags, class and every vertex inside the written cells are stored, and the 13,340 lines and 17,519 areas that lie wholly inside keep their length (within 0.5 m) and area (within 2 cm times the perimeter; the rounding of a cut's two border points to 1e-7 degrees, about 1 cm, makes the area error absolute); the 205 assembled multipolygons wholly inside (180 of them with holes) keep their area; the 2 incomplete ones are outlines only; the Watch copy is a subset; builds are deterministic.
- **Observation for the style:** with rule table version 1 about a third of the stored features had class `other` (individual trees, crossings, bus stops, fences and walls); version 2 splits them out, see question 47. The numbers above are from version 1; with version 2 the full store is 3.94 MB and the Watch copy 1.69 MB at 10 km, 5.05 MB and 2.23 MB at 15 km.

### Map style (decided, `MapStyle`)

- **A style is Swift data, keyed by class.** `MapStyle` holds a background colour and a `ClassStyle` per `FeatureClass`; it never looks at raw tags. A class without an entry is hidden, which is how the Watch style leaves classes out. `MapStyle.standard` (iOS, iPadOS, macOS) styles every class except `other`; `MapStyle.watch` styles the Watch profile only, from zoom 12, with thicker lines, no dashes, a road outline only when zoomed in, and labels only for places.
- **Zoom-dependent values** are `ZoomValue<T>`: stops over fractional zoom, linear interpolation, constant outside the first and last stop. It works for numbers and for `MapColor` (sRGB, no SwiftUI or Core Graphics dependency, so the target builds everywhere).
- **A `ClassStyle`** has an optional fill (areas), stroke (lines and area outlines, with casing, dash, cap and join), point symbol and label, a `visibleZoom` range on top of the store's bands, and a `layer` for drawing order (lowest first; trails are above roads). `visibleClassIDs(atZoom:)` gives the set for `FeatureStoreFile.features(in:band:classes:)`, so hidden classes are skipped without decoding.
- **Road width from `lanes` (decided).** `LineWidth` is a legible screen width by zoom (`points`, also the minimum) plus an optional `GroundWidth` (metres per lane, default lanes, a cap). The renderer passes the zoom, the metres per point at the current latitude and the feature's `lanes` tag; the width is `max(points, lanes × metresPerLane / metresPerPoint)`. Zoomed out, every road keeps its legible width; zoomed in, a four-lane road is drawn twice as wide as a two-lane road. Untagged or invalid `lanes` (below 1) use the default (2); values above 12 are capped. `lanes` is the only tag the renderer reads for drawing, and it is available in the detail band only (tags are stored there); other bands use the default. Roads (`roadMajor`, `roadMinor`) get a `GroundWidth` and a casing (outline): the renderer strokes the casing at `width + 2 × extra` first and the fill on top, so a zoomed-in motorway shows as a fill with an outline. **Crossings at the same level:** road classes put their casing on a shared `casingLayer` below all their fills, and `MapStyle.drawSteps(atZoom:)` returns casing steps before body steps, so the renderer draws every outline first and every fill after; at a crossing the fills run through each other's outlines and the outlines join. The renderer does the same inside one class (all casings of the class, then all strokes). Bridges and tunnels (the `layer` tag) are drawn as their own casing-plus-fill group above or below, which is renderer work (`MapRender`); the extra width is a `ZoomValue` that grows with zoom (0 means no outline); paths and tracks keep screen widths. A `width` tag in metres and one-way lane splitting are not used yet.
- **Not decided yet:** JSON or another external style format (question 15). The model has no `Codable` conformance yet; add it when a second style source exists.

### Map scene (decided, `MapRender`, part 1)

`MapRender` is built in two parts: first a scene with no graphics dependency, then the drawing backends.

- **`MapViewport`:** centre, fractional zoom and size in points. Web Mercator with 256-point tiles (the world is `256 × 2^zoom` points wide), north up, no rotation in v1. Screen positions are computed relative to the centre in `Double`. It gives `metresPerPoint` at the centre latitude (for the `lanes` road width) and the storage cells that touch the view, with a margin. Views over the antimeridian are not supported (columns are clamped, not wrapped).
- **Band choice:** below zoom 12 overview, 12 to below 15 mid, 15 and up detail (the provisional boundaries). If the file lacks the band (the Watch has no overview), the nearest finer band is used, then the nearest coarser. Above the detail band the detail geometry is scaled (overzoom); there is nothing to decode extra.
- **`MapSceneBuilder` / `MapScene`:** reads only the cells in view, one band and the classes the style shows (the others are skipped by length in the file), joins line pieces, projects, culls and returns the steps in `MapStyle.drawSteps` order. It is rebuilt when position or zoom changes; on the Watch the app decides when (see Battery). The scene is plain `Sendable` data, so tests need no graphics context and any backend can draw it.
- **Joining clipped lines (decided):** pieces of one way join when the first has `continuesAfter`, the second `continuesBefore`, and the end vertices are within 3 units of 1e-7 degree (about 3 cm; each cell rounds its own clip point). The order is the stored `offsetAlongLine`. A line that leaves and re-enters a cell stays two lines. Areas are not joined: each cell's piece is filled on its own, and its outline leaves out the artificial (cell-border) edges, merging a run that wraps around the ring start.
- **Tags read for drawing:** `lanes` (detail band only) and `name`. Nothing else.
- **Not yet:** bridges and tunnels, a cache of decoded cells, labels along lines.

### Drawing backend (decided, `MapRender`, part 2)

- **`MapRenderer`** is a protocol with one method, `draw(_:style:into:)`, and an associated `Target`. Everything that depends on data or style (decoding, band choice, joining, culling, ordering, label placement) happens before it, so another backend (Metal, SwiftUI `Canvas`) only has to turn steps into drawing calls. `CoreGraphicsRenderer` (target `CGContext`, screen points with the origin top-left and y down) is the first backend and the only one that uses Core Graphics and Core Text; it builds for all four platforms. A SwiftUI `Canvas` view can call it with the `CGContext` it gets from `Canvas`.
- **Drawing order:** background, then each `SceneStep` in order (casings first, so outlines of crossing roads join), then labels on top.
- **Areas:** filled with the even-odd rule (holes stay empty); an incomplete area is not filled, only outlined. A fill without outline gets a 0.5 pt hairline in the fill colour when it is opaque, which closes the seams between the pieces of neighbouring cells. The outline strokes real edges only.
- **Labels (decided for v1):** horizontal text only (Core Text, Helvetica, halo as a wider stroke under the fill). `LabelCandidates` collects named points and areas that have a label style; `LabelPlacer` places them greedily by priority (then OSM ID, so the result is deterministic): points try right, left, above and below the symbol, areas are centred. A label must lie wholly in the view and may not overlap another label or any point symbol; otherwise it is dropped. One label per feature (the largest piece of an area wins). Lines are not labelled yet.
- **Attribution (decided):** the scene carries the store file's `attribution` string and every backend draws it small in the bottom-right corner, so no image derived from OSM data leaves without the ODbL credit. An empty string draws nothing. How it is shown is a style setting, `MapStyle.attribution` (`AttributionDisplay`): `full` (the whole string; the default and the `standard` style), `compact` (a short "© OSM" mark; the `watch` style, because the full text takes too much of a Watch screen) or `hidden`. With `compact` or `hidden` the app must make the full credit reachable elsewhere, for example in an About or Data screen, using `FeatureStoreFile.attribution`; exported images should use `full`. The OSM Foundation's guidelines accept a credit in a place users expect it (an About screen or a © control) for interactive maps, but this is not legal advice and stays on the release checklist (section 9). The CLI exposes it as `--attribution full|compact|none`.
- **PNG:** `pngData(for:style:scale:)` draws into an sRGB bitmap (scale 1 to 8, at most 16,384 px per side) and encodes with ImageIO. `geomapkit render` in `Tools/` uses it, and prints scene and draw times.
- **Measured (Mac, release, Liechtenstein 10 km store):** a 900 × 700 pt view at zoom 16 reads one cell and draws 3,003 features in 18 steps: scene 0.01 s, draw and PNG encode 0.09 s at scale 2. At zoom 13.5 (mid band, 12 cells, 6,225 features) 0.01 s and 0.07 s. These are Mac figures; the Watch cost is not measured.

## 5. Corridor (Watch data)

**The track is known beforehand (decided; v2, since v1 has no tracks).** For longer runs, ultras especially, the user has a track before the run: a GPX file, or a track created in an app that uses this package on macOS or iOS. The corridor is therefore cut from that track plus a buffer, before the run, on the phone or Mac; the phone does all the cutting and the Watch only asks for an area (see "Watch map data requests"). The v1 corridor holds map features only (the graph part below is v2). Open: runs without a track (question 42).

When a route is sent to the Watch:

- Take all edges within a buffer of the route polyline (starting guess 300 m to 1 km, configurable), plus the junction nodes they connect.
- Edges that cross the buffer boundary are clipped at the nearest node, and those nodes are marked as boundary nodes.
- The result is a few hundred KB at most and uses the same graph format as the regional graph, so the same router code runs on the Watch.
- Corridor features are cut from the regional feature store by spatial cell. Both files go over WatchConnectivity file transfer with the route.
- Edge attributes must be rich enough for all cost profiles (running, walking, cycling), since the Watch cannot fetch more.

## 6. Off-route handling and rejoin

`RouteFollower` owns progress (distance along the route polyline) and off-route detection. Rejoin is a single multi-target search in `Router`:

1. Candidates are route nodes within a search radius, filtered by progress (see below).
2. Search from the runner outward and stop on any node in the target set.
3. Score each candidate as `cost(runner to rejoin point) + cost(remaining route from that point)`. Rejoining further ahead skips route, so the remaining cost drops and that candidate wins when the detour is cheap. Rejoining behind adds already-run route and is penalized or disallowed.

Who reroutes:

1. Phone reachable: ask the phone (full graph, full cost model).
2. Phone not reachable: run the search on the corridor graph.
3. Outside the corridor: no graph is available. Show a straight-line bearing and distance to the route, and say so in the UI.

A Watch reroute is marked provisional and reconciled when the phone is back.

Behaviour rules:

- Candidates use progress as well as proximity, so loops, self-crossings and out-and-back routes do not snap to the wrong pass.
- Hysteresis: require the off-route distance to exceed a threshold for several seconds, and do not replan again until the runner has moved some distance.
- Stability: stick with a chosen rejoin plan unless the runner clearly deviates from it.
- `RejoinPolicy` holds the tunables: search radius, backward allowance, skip limit, mandatory waypoints.

44. Areas that cross a source boundary (for example Norway and Sweden): a single country file holds only its own objects, plus whole ways and relations that cross the border, so a box over both countries comes out as half a map (Liechtenstein showed 130 of 342 routes incomplete for this reason). Planned: `AreaCutter` takes several readers, runs each pass over all of them, de-duplicates objects by ID (nodes need a unique-by-ID step; ways and relations are already keyed by ID), and completes relations across files. Conflicting versions of one ID: the first file wins, so the caller orders the files; both files should be downloaded on the same day. In phase 2 the hosted area files are produced from source data that covers the border, so users never see it, and areas are defined by bounding box, not by country (question 24).
45. Source data manager (planned, `Regions` target, to be built after the feature store): given a requested area, find the source regions that intersect it (a catalog of regions with outlines, licences and credits; Geofabrik publishes an index of regions with outlines, to verify), check the local cache and download what is missing. Each cached file records its URL, size, download date and `ETag`/`Last-Modified`. Staleness: after a time limit (suggested 30 days) send a conditional request with the stored `ETag`; "not modified" only refreshes the check date, a changed file is downloaded; the app asks the user and never downloads on its own. Downloads go to a temporary file, are checked for size (and the published checksum if any) and then moved into place, so a failed download never replaces a good file; support resuming, a free-disk-space check, progress, and background `URLSession` with Wi-Fi only on iOS. The network sits behind a protocol so tests use a fake downloader. A built store records the source files and dates it was derived from, so "this area is out of date" is a comparison (also question 30). Geofabrik asks for considerate use, so this is mainly the phase 1 and server-side production tool; user devices in phase 2 download small hosted files from our own manifest.
