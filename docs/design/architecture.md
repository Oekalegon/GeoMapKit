# GeoMapKit: architecture (first draft)

Status: draft from the first design discussion, 2026-11-06. Nothing is built or verified. Background on frameworks, data sets and licences is in `maps-summary.md` (TrainingApp repo, `docs/design/`); those facts come from memory and need checking.

## 1. Goals

- A mapping kit for iOS, iPadOS, macOS and watchOS, used first for trail running (also walking and cycling).
- Combine data from several sources into tiles, render them with our own renderer, and route with our own router.
- Offline first. Small areas (a valley, a city), not whole countries.
- Pure Swift in the core targets so everything builds for watchOS.

### Battery (watchOS first, not a concern on macOS)

A cross-cutting constraint. A trail run can last hours with GPS, heart rate and the display all active, so the map must add as little as possible. Principles:

- **Draw only when something changed.** Redraw on a new position fix, a Crown turn or a screen wake, never on a timer. No continuous animation.
- **Always-on display:** a reduced, static view (route, position, no animation), redrawn at most about once per second, or per the system's cadence.
- **Cache the rendered view** and move it for small position changes; rebuild only when the position leaves the cached area or the zoom changes.
- **Precompute on the phone,** never on the Watch: simplification per zoom, the corridor graph, the feature cells. The Watch only reads.
- **Memory-mapped, read-only data** with no decode-everything step, so wake-ups stay cheap.
- **Reroute on the Watch is rare and bounded:** it runs only when the phone is out of reach and the runner is off route, on the small corridor graph, with an iteration cap.
- **Location updates and sensors belong to the app's workout session,** not to the map; the kit takes positions as input and does not start its own location updates.
- **Measure:** an energy budget per feature (Instruments Energy Log on a real Watch) is part of definition-of-done for the renderer and the follower.

## 2. Decisions so far

| Topic | Decision |
|---|---|
| Renderer | Own renderer. Core Graphics / SwiftUI `Canvas` backend first, behind a `MapRenderer` protocol. A Metal backend on iOS only if profiling shows a need. |
| Router | Own router. One implementation (A*) for phone and Watch. |
| Map data format | **Own feature store, no MVT and no PMTiles.** All map data comes from our own OSM processing; outside tile sources are not a requirement. Parsed OSM features are stored in a compact format of our own, grouped spatially (by z/x/y or a similar grid) so a Watch corridor can still be cut by region and the renderer loads only what is on screen. |
| Planning | On iPhone, iPad or Mac, on a regional graph for a small downloaded area. |
| Watch | Receives the route, a corridor graph and corridor tiles. It follows the route and only reroutes when the phone is out of reach. |
| Rejoin | After leaving the route, reroute to the best nearby route point, not necessarily back to the exit point (section 6). |
| Route types (v3) | A to B with via-points, out-and-back, and import of a GPX track with map-matching to the graph. No loop generation in v1, but `Router` stays usable by a future loop generator. |
| Activities (v3, routing) | Running and walking (one profile family). Cycling is not in v1, but its edge attributes (one-way, `bicycle` access, `mtb:scale`) are stored in the graph from the start so graphs need no rebuild later. |
| Waypoints | Waypoints carry a `required` flag. A rejoin cannot skip past the next unreached required waypoint. Via-points placed while planning are required by default; optional points of interest are not. |
| Pipeline | Graph building happens **on device**, in Swift, in the package (OSM data for a user-chosen area in, routing graph out). Pre-built server files are not the v1 path. |
| OSM input | OSM data comes as **PBF** (`.osm.pbf`) from the start, read by a Swift PBF reader in the package (`OSMPBF` target). Overpass is not used. The reader sits behind an `OSMDataSource` protocol so the origin of the bytes (bundled file, download, our own host) can change. |
| PBF sourcing | Phase 1: a **test Mac app** that uses the package and downloads full regional PBF files (for example from Geofabrik), cuts the chosen area and builds graph and map data. Phase 2: smaller area PBFs hosted on a server of ours, downloaded by the apps. The area-cutting code lives in the package, so the same code later produces the hosted files. |
| Elevation (v1) | No DEM in v1. The cost model uses tags only (surface, `sac_scale`, road class). The graph format reserves optional ascent/descent fields so a DEM step can be added later without a format break. The Watch barometer remains the source for recorded elevation. |
| Distribution | The kit will be distributed at some point, so licence, attribution and data-source terms are release gates (section 9). |
| Release plan (provisional) | **v1 is map rendering only, on all platforms.** v1: PBF reader, area cutting, lossless feature store, style and labels, the renderer on iOS, iPadOS, macOS and watchOS, a map view with pan, zoom and rotation (scroll-wheel zoom on the Mac), and delivery of a map region to the Watch (a region cut on the phone or Mac, with no track involved). **Not in v1:** tracks, GPX, route following, track-based corridors and routing. **v2:** tracks (GPX import, a `Route` model, overlay, `RouteFollower`, corridor cut from a track). **v3:** routing (graph builder, router and cost model, route planning, map-matching, rejoin rerouting). The track and routing decisions in this document are the design for those later steps. |
| Off-trail (v2, provisional) | A track created beforehand (for example on the Mac) may go off-trail, and the app must follow it. Orienteering itself is not a use case: routing and tracks are not allowed in competition, so there is no orienteering mode, no ordered controls and no punching. Nothing in v1 may assume that a route lies on paths. A route is an ordered polyline with waypoints, and each leg can be a free leg (straight or free-form, not on any path) or, in v2, a leg on the path network. `RouteFollower` works on any polyline without a graph. Off-route detection on a free leg uses the same rules as on any track. The Watch corridor stays a ribbon around the track. Terrain-cost routing across land cover is not planned (question 41). |
| Access and sidewalks for routing (decided, v3; not built) | **The data is kept.** The feature store keeps every raw tag in the detail band, and sidewalks and crossings that are mapped as their own ways are stored (class `pavement`, drawn only faintly from zoom 15); a sidewalk mapped as a tag on the road (`sidewalk=both`, `left`, `right`, `no`, and `cycleway=*`) is part of the road's tags. The graph builder reads the extract's raw tags, not the classes, so what the style draws does not limit routing. **Access is resolved once, in the graph builder, into per-edge flags** by one rule table kept per country: (1) explicit tags win (`foot`, `bicycle`, `access`, `motor_vehicle`, with `no`, `private`, `yes`, `designated`, `permissive`); (2) road-wide flags next (`motorroad=yes` allows neither pedestrians nor cyclists); (3) then the defaults of the road type, where `motorway` and `motorway_link` allow neither and the other types allow both (in Norway some trunk and primary roads are signed closed to pedestrians or cyclists without a tag, so the default for them is a guess and the cost model should treat a missing tag as a mid value, never the easiest, as it does for surface); (4) `segregated`, `foot=designated` and `bicycle=designated` on footways and cycleways. The edge gets *can walk* and *can cycle* and a *sidewalk beside the road* attribute from the road's own `sidewalk` tag (none, one side, both); a plain footway beside a road that carries no `footway=sidewalk` tag cannot be told from a park path by tags, so it needs a geometry test (a footway that runs close and parallel to a road) before it counts as a sidewalk. Routing runs on the phone or Mac. **The corridor sent to the Watch carries only these derived flags**: about one byte per edge (walk and cycle in one bit each, the sidewalk attribute in two), never the raw tags or the country rule table, so a reroute on the Watch (phone out of reach) cannot send a runner onto a motorway or a private road, and the same router code runs on both. If the corridor needs a size limit, these flags are the last thing to cut. The Watch feature copy stays tagless. |
| Cost model (v3) | A `CostProfile` is a table of weights (data, not code), chosen by user preference. Presets: trail running, road running, walking. Adjusted by a few user settings: road avoidance, surface preference and a maximum difficulty (`sac_scale` limit). `mountain_hiking` is acceptable when the user allows it; the limit is a user setting, not a fixed exclusion. Default limit: up to `mountain_hiking` (to confirm). Missing tags default to a mid value, never to the easiest. A full per-surface weight editor is deferred; the data-table design allows it later without a router change. The A* heuristic is computed from the fastest speed of the profile in use, so it stays admissible. |
| Platforms | Minimum version 26 on all platforms: iOS, iPadOS, macOS and watchOS. No availability checks for older systems. |
| Language | Swift 6 language mode with strict concurrency from the start. Value types and `Sendable` by default; explicit isolation (actors) for caches and file readers. |
| Numeric types and geometry conventions | `Int` may be 32 bits on some Watch hardware (to verify), so OSM IDs and file offsets use explicit `Int64`/`UInt64`. `TileID.maximumZoom` is 30 so `1 << zoom` is safe there. Longitude +180 is treated as -180 (column 0); bounding boxes crossing or ending at the antimeridian are not supported. Computed tile corners are not used to identify a tile (floating-point rounding); use a point inside it. Decoded tile IDs are validated, since they arrive from manifests and Watch requests. |
| Extract representation | An `OSMExtract` stores nodes, ways and relations in columns (IDs, coordinates as 32-bit integers in 1e-7 degrees, flat vertex and member arrays) with tags as ranges of key and value IDs into one shared table of distinct strings. Strings are interned **byte for byte**, not with Swift `String` equality, which treats canonically equivalent strings (for example a precomposed and a decomposed "é") as equal and would silently merge different data; the reader keeps tags as an ordered list of `OSMTag` for the same reason (question 46). Tags are kept in key order so output is deterministic. Elements (`OSMNode`, `OSMWay`, `ExtractedRelation`) are built on demand; accessors read the columns without allocating. Oslo, 15 km: the extract's data is 164 MB in columns (`OSMExtract.memoryBytes`, stable); the process footprint with the extract alive was 860 to 930 MB as dictionaries and 220 to 440 MB compact over several runs (the figure varies with how much freed memory the allocator has not yet returned, so `memoryBytes` is the reliable number); the cut's peak heap fell from 899 MB to about 445 MB. Verified by a content digest identical to the dictionary version on Liechtenstein and Oslo. |
| Feature store file format v1 | Implemented in `FeatureStore` (`FeatureStoreWriter`, `FeatureStoreFile`). Little-endian; a 144-byte header (magic `GMKM`, format version, classifier version, storage zoom, band mask, cell count, bounding box and source date, file length, six section ranges) and a CRC-32 in the last four bytes. Sections: cell index (24-byte entries `x, y, offset, length`, sorted by `(x, y)`, binary search), cell blocks, string offsets, string bytes, relation table (sorted by ID, binary search), attribution. A cell block stores its own origin (not derived from the tile, so files from other platforms agree) and three band bodies; a band groups features by class, so a hidden class is skipped by its byte length. Features carry object type and ID, piece flags (`continuesBefore`, `continuesAfter`, `incomplete`), subclass, name ID, offset along the line in cm, tags (written as given in every band; the builder gives all tags in the detail band and none in the others, except the value of the `landuse` or `natural` tag of a `landUse` feature; a reader must not assume empty tags outside the detail band) and parts of vertices delta-coded as zigzag varints in 1e-7 degrees, with artificial-edge runs. The string table is byte-exact and renumbered by use count (most used string = ID 0). Opening checks only header and section ranges (cheap, for the Watch); lookups validate what they touch; `verify()` checks the CRC and the whole structure and runs after a transfer. Every read is bounds-checked and counts are capped by the remaining bytes. Output is deterministic. Decided with this: `FeatureStore` holds format and reader (Watch-safe); the builder will be a separate target `FeatureStoreBuilder` that depends on `OSMPBF`, so the Watch does not link the PBF and Compression code. Incomplete multipolygons are outline-only as a whole (all or nothing). Route-relation assembled lines are deferred. Question 46 (ordered byte-exact tags) is resolved. For question 45 the recommendation is one store file per block (for example a z9 or z10 tile) plus a manifest, with a reader that routes by cell, so no merge step is needed. |
| Own coordinate types | `GeoCore` uses its own `Coordinate` (and later its own live-position type for `RouteFollower`), not `CLLocationCoordinate2D` or `CLLocation`, so the core stays free of Apple frameworks (hosted area files may be produced on Linux) and the type is `Hashable`, `Codable` and under our control. Conversions to and from CoreLocation types live in a small adapter wrapped in `#if canImport(CoreLocation)`. `Coordinate` is immutable and its initializer does not validate (no failable init at every call site); consumers handle bad values, and `isValid` is available where strictness is needed, for example when reading untrusted files. |
| Overlays (v2) | A generic `MapOverlay` protocol (points, lines, polygons with a style). Only GPX tracks in v1 (the planned route and the current track). The kit knows nothing about Strava or HealthKit. |

## 4. Data products

From the same OSM source (plus DEM and land cover) the pipeline makes two products:

1. **Render features:** our own feature store, spatially grouped, with per-zoom simplification baked in. (Contours and hillshade are out of v1 because there is no DEM.)
2. **Routing graph:** a compact binary file. Nodes at junctions, edges with length, surface, `sac_scale`, access and ascent/descent from the DEM. Memory-mapped, fixed-width arrays (CSR adjacency), versioned.

Rendered tiles are generalized and clipped, so they cannot be used for routing.

### Feature store layout (decided)

- **Cells:** the standard z/x/y Web Mercator grid at one fixed storage zoom (z13, decided). The index is a sorted, memory-mapped array of `(x, y) -> offset, length`.
- **Bands:** simplified geometry is baked in per zoom band (starting guess: overview z8 to 11, mid z12 to 14, detail z15 and up). The Watch never simplifies. Every feature has a minimum band, so the reader can skip it without decoding.
- **Geometry:** integer coordinates in OSM's native 1e-7 degree units, relative to the cell origin, delta-coded as varints. This is lossless against the OSM source (a coarser grid would quantize it). Simplified bands are extra copies; the detail band is the original geometry.
- **Clipping:** lines and polygons are clipped at cell edges. Every feature has a stable ID (OSM way or relation ID). Each clipped piece carries the ID, `continuesBefore`/`continuesAfter` flags, and its offset along the line (measured along the geometry of the band that is drawn, which is the original line in the detail band), so the renderer can join pieces, keep dash patterns continuous, draw one label per feature and hit-test whole features. Polygon edges that lie on a cell border are marked artificial, so they are filled but not stroked.
- **No loss of OSM data on macOS and iOS (decided):** the store keeps the same feature granularity as OSM. Every feature (node, way, relation as modelled) is stored with **all of its tags**. A shared dictionary of keys and values and a per-feature list of dictionary indices keep this compact without losing anything. The builder additionally derives a compact **feature class** plus flags for rendering; the class is derived data and never replaces the tags, and features the classifier does not recognize are kept with class `other`. The renderer and style work on classes; everything else (search, inspection, the graph builder, future styling) can read the raw tags. A shared string table holds names and other values.
- **Two files plus a manifest:** `map` (features) and `graph` (routing), with a shared header, version and bounding box. Map features and graph edges share the OSM way ID.
- **Layer profile:** which classes show at which band is a user setting on macOS and iOS (class to lowest visible band, or hidden), applied when reading, so a change needs no rebuild. The Watch has no setting: the phone applies the profile when it cuts the corridor and drops hidden features from the Watch copy. A profile change reaches the Watch with the next corridor.
- **Watch shows less than iOS (decided):** for the same workout and scale, the Watch map shows only the **essential minimum**: what a runner needs while running (the route, the runner's position and the trail or path they are on, with a few anchors such as junctions, water and major roads where useful). Everything else is left to the iPhone: when the runner is lost or wants detail, they use the phone. The Watch feature set is therefore a smaller, fixed profile applied when the corridor is cut, not the user's iOS layer profile. Exception: if the runner has only the Watch with them (no phone), the Watch may need a richer set (for example more path context for navigating when lost). Open: how the Watch knows it is phone-less (phone not reachable) and whether it then switches to a richer profile, which would require the richer features to be present in the corridor already (see question 37).
- **Relations (decided):** all relation types are stored losslessly, as tags plus an ordered member list with roles (member type, ID and role), whatever the type. In addition, the builder derives **assembled geometry** where it helps drawing: multipolygons are assembled into area features with holes (outer and inner rings joined from member ways), and hiking/running route relations get an optional assembled line for drawing and labelling. Assembled geometry is derived data and never replaces the membership list. Relations spanning several cells are stored once, with the member IDs resolvable across cells.
- **Areas that span cells or the extract (decided):**
  - Clipping happens on the **complete assembled polygon**, never on a partial one. Edges that the clip creates along a cell border are marked artificial; the renderer fills the clipped ring and strokes only real edges. Neighbouring cells hold their own piece of the same area and meet at the border, so the area looks continuous. Draw fills without an anti-aliased outline (or with a tiny overlap) to avoid hairline seams between cells.
  - The area cut (see question 31) **completes relations that touch the box**: all member ways of a touching relation are kept whole with their nodes, so multipolygons can be assembled. Completion has a size limit; relations above it are marked incomplete.
  - An area that still cannot be assembled gets an `incomplete` flag and keeps its membership list. The renderer draws the known outline as a line and does not fill it; it never guesses the inside from an open ring.
- **Watch zoom limits and ultras (proposed numbers):** live view zooms out to about 30 km across and in to about 100 m across, with the basemap drawn inside the corridor only. Ultra marathons (50 to 170 km and longer, 10 to 40 hours) are in scope. For a whole-route overview, which may span 100 km or more, the Watch draws a simplified route line plus waypoints (aid stations, the runner's position, remaining distance) and no basemap features, as a separate mode. This needs no overview band. Ultras make these points matter more: very tight battery over 24 hours or more, long corridors (question 39), phone-less runs (question 37), required waypoints at aid stations and checkpoints, GPX import as a main use case, and routes that cross themselves, which makes progress-along-route tracking essential.
- **Ultra hardware assumption (to verify):** ultra runs are assumed to use an Apple Watch Ultra with the maximum battery-saving workout mode. The specs of the newest model are unconfirmed. The principles stay the same on every Watch. Consequence for the kit: do not assume a position fix every second. In power-saving modes GPS and heart rate are sampled less often, so `RouteFollower` thresholds (off-route distance, hysteresis, rejoin tolerance) depend on the observed fix interval and speed, which are inputs; positions between fixes are interpolated along the route; live snapping reports a confidence and does not jump between passes on loops and self-crossings. Tests must include sparse tracks.
- **Watch zoom range (decided):** on the Watch the user does not zoom out further than tens of kilometres for running, or hundreds of kilometres for cycling. The corridor therefore does not need the overview band for running. Overview geometry stays an iOS/macOS concern. A zoomed-out Watch view shows the route and the corridor ribbon around it, and there is no basemap outside the corridor to draw. Cycling is not a Watch map use case (decided): a Watch is not usable as a map while cycling, and cyclists use an iPhone on a handlebar mount. Residential streets are in the mid band and so in the Watch copy (rule table 10), which is what a runner in a town needs at zoom 14; buildings are not on the Watch. So there is no cycling corridor strategy or coarser Watch band; the Watch map is for running and walking. Cycling is served by the iPhone (and iPad/Mac), which has the full regional graph and all bands. Cycling edge attributes are still stored in the graph (see Activities).
- **Watch map data requests (decided):** the Watch requests map data from the iPhone whenever the map is used and the Watch does not have data for the area on screen. The phone does all the cutting; the Watch only asks for an area (a set of z13 cells) and stores what it receives. The phone supports **predownloading of areas**, so the data is normally already on the phone when the Watch asks. Triggers: (1) when a run is started, or when the map app is started on the Watch, it requests an area around the current location, or, once tracks exist (v2), around the track; (2) afterwards new data is requested only when the runner leaves the held area, which should be very rare. Assumption for a run without a track: the distance is under 25 km and probably a round trip, so a **15 km radius around the start** is enough; leaving it is expected at most once per run, if at all. Very long runs are the exception, and they will normally have a track. If the phone is unreachable when the runner leaves the area, the Watch keeps drawing what it has and the runner's own trail, with a notice that the map has ended. Cells are sent nearest-first so the map appears quickly.
- **Classes are not a filter at build time:** because nothing is dropped, the earlier idea of core and optional classes chosen when an area is built is superseded (reinstate it only if area size turns out to be a problem). What is shown is decided by the layer profile (iOS/macOS) or the fixed Watch profile (corridor cut), both working on derived classes.

### Feature classes (decided, `FeatureClassifier` rule table, current version in the text below)

An ordered rule table; the first match wins, so an object has one class, and the raw tags are always kept. Version 1 had 17 classes; **version 2** (question 47, plus power lines, ski pistes and lifts as navigation landmarks) appends classes 17 to 23, and the numbers of the existing classes did not change; **version 3** appends class 24, `countryBorder` (a national border, `boundary=administrative` with `admin_level=2`, so the standard style can draw it as the boundary line on a wide, solid, transparent band of the same colour; the Watch does not draw boundaries). Files built with an older table keep their borders in `boundary` and need a rebuild to get the new class. **Version 4** (from an analysis of Oslo with `geomapkit inspect`, which found that 28% of all detail features were `other`, 80% of those objects with nothing but an address) appends classes 25 to 27: `address` (objects whose only tags are `addr:*`, kept for search and never drawn), `pavement` (`highway=footway` with `footway=sidewalk`, `crossing`, `traffic_island` or `access_aisle`, checked after the rule table like `countryBorder`, detail band, not on the Watch; the standard style draws it fainter and thinner than a path, from zoom 15, under the paths) and `cliff` (`natural=cliff`); it also classifies place values (`farm`, `islet`, `neighbourhood`, `quarter`, `square`), `railway=subway` and `monorail`, rail crossings, switches, signals and buffer stops and `traffic_calming` (as `roadPoint`), `power=pole` and `portal`, `waterway=dam` and `weir`, `natural=shrubbery` and `shrub`, `landuse` village_green, recreation_ground, flowerbed, farmyard, garages and railway. Measured on Oslo (15 km, 847,335 objects): `other` fell from 240,025 to 35,602 objects (192,263 became `address`); what stays `other` is mostly bare `area=yes` outlines (13,367), grave nodes (`cemetery=grave`, 13,316), building entrances (2,400), rooftop solar panels (1,180) and single stones (1,085), none of which a runner navigates by. Explicitly tagged sidewalks and crossings were 16,048 of the 82,894 path objects; the rest of the footways, about 28,000 plain `highway=footway`, carry no tag that tells a sidewalk from a park path, so telling them apart needs geometry (a footway that runs beside a road) and is not done yet. **Version 5** appends `sea` (28, a polygon the builder makes, never classified from tags) and `coastline` (29, `natural=coastline`, overview band, not on the Watch); a style file written before they existed shows no sea until it lists the classes. **Version 6** makes `natural=coastline` win over every other key (an island way that is also `place=islet` or `place=island` was classed as a place and an area, so the island had a sea hole but no shore line; found in Lofoten, where it hit most islands) and always a line; a coastline that is a multipolygon relation (an island mapped that way) is stored as lines too, not as an area. **Version 7** appends `roadArea` (30): a road, track or path that is an area (`area=yes` with a `highway` tag, or a road mapped as a multipolygon: a yard, a pedestrian square, a parking aisle drawn as a polygon). It used to keep the class of the road and be drawn as the outline of the polygon stroked at the width of a road, which gave a wide white band with no casing (found in Skjetten, Oslo: a service yard drawn as a thick ring around a building). The standard style fills a road area white with a thin grey outline, from zoom 14, on layer 13: over the land cover, under the buildings (14) and under all roads; the Watch does not draw it. **Version 8** also takes a `highway=footway` for a sidewalk (`pavement`) when it runs beside a road, whether or not it carries `footway=sidewalk`: `RoadIndex` puts the roads of the extract (`roadMajor` and `roadMinor`, but not pedestrian streets and not tunnels) in a grid of 15 m cells, in metres from a flat projection at the middle latitude of the extract, and the footway is a sidewalk when at least 60% of its length (tested at points 5 m apart, at least 10 m of it in all) lies within 15 m of a road segment that runs the same way, within 25 degrees; a footway that crosses a road, ends at it, or runs through a park does not qualify, nor does one with a trail tag (`sac_scale`, `trail_visibility`, `mtb:scale`, `informal`, `trailblazed`, `hiking`). `highway=path`, `cycleway` and `steps` are left alone. On Oslo (15 km) this moved 3,636 more footways to `pavement` (the tagged ones were 16,045; 12 m would have moved 2,626 and 20 m 5,276, at the price of paths that happen to run alongside a road): the building cost 0.5 s more of the 7.5 s build. The park paths of Frogner stay paths in a before and after render. **Version 9** adds a second test for the footways that are not beside a road: a footway is also a sidewalk when at least 70% of its length (tested the same way, at least 10 m in all) lies in a built-up area and not in a green one. `TownIndex` takes the closed ways and the complete multipolygon relations (with their holes, by the even-odd rule) with urban land use (`landuse` residential, industrial, commercial, retail, construction, military, farmyard, garages, railway), road areas (pedestrian squares, yards), car parks (`amenity=parking`), squares (`place=square`) and platforms (closed ways only) as built-up, and those with land cover or woods (parks, gardens, meadows, heath, `natural=wood` and so on) as green. A park that is a relation must count, or its paths would become sidewalks because the closed way of the housing around it is seen. The grid has 100 m cells; a polygon whose box covers more than 400 cells (a wood of many kilometres) is kept in a short list that every query tests, so it does not take tens of thousands of cells. Distances come from `LocalMetres`, a flat projection around the middle latitude of the extract (until rule table 12 it scaled east-west by the cosine of each point's own latitude, which shears the plane in proportion to the longitude: 100 m north at 25 degrees east also moved 37 m east, found in the review of version 13; lengths were off by up to 7%, and the tolerances of 6 to 25 m were not affected in practice). The build report counts the areas used. On Oslo (11,664 built-up and 24,093 green areas used) this moved 6,973 more footways, after the 3,710 beside roads (path 66,724 to 56,052, pavement 16,045 to 26,717), the build 1.2 s longer (8.7 s) than before the footway rules; the city centre loses most of its red footways, and the paths of Frogner park, which lies inside a built-up area but also in a park, stay paths. About 18,000 footways in Oslo are still plain footways (inside multipolygon areas, in stations, or really paths). **Version 10** moves the minor roads (`residential`, `service`, `living_street`, `pedestrian`, `road`) and buildings from the detail band to the mid band: a street is as runnable as a path, and paths are in the mid band, so a map that shows the paths shows the streets (a `service` road, which is a driveway or a way through a yard, is runnable too). At zoom 14 the map is drawn from the mid band, and without them a town was blank between the main roads: the sidewalks (paths, drawn from zoom 12) had been the only streets visible there, and the rule that takes them for pavement (versions 8 and 9) took even those away. The standard style draws buildings from zoom 14 as a fill only, with the outline fading in between 14.5 and 15. On Oslo (15 km) the file grows from 54.7 to 65.3 MB (the mid band from 5.5 MB with 121,000 features to 16.1 MB with 419,000, the build from 8.7 to 10.1 s) and the Watch copy from 15.5 to 17.2 MB (the Watch copy has the streets but not the buildings). 16,239 rings (small buildings) are too small for the mid band after simplification and are only in the detail band; the build report counts them. A style file written before `pavement` existed hides sidewalks until it lists the class (a fallback to `path` would have made the Watch style fail its round trip). **Version 11** gives `highway=service` its own class, `roadService` (31), still in the mid band and on the Watch: it is drawn thinner (about two thirds of a street, one lane wide by default) with a lighter casing, on the same layers as the streets so crossings join, and a style file written before it existed draws service roads as streets. **Version 11** also puts urban land use (`landuse` residential, industrial, commercial, retail, construction, military, farmyard, garages, railway) and the large kinds of land cover (every `natural` kind, and `landuse` meadow, farmland, orchard, vineyard and quarry) in the overview band, so that at zoom 11 a village differs from the fields, heath and bare rock around it (before, both had nothing to draw at zoom 11); the small kinds (lawns, allotments, village greens, recreation grounds, flower beds and the `leisure` kinds) start at the mid band. The standard style shows urban land use from zoom 9 and land cover from zoom 10. On Oslo this makes the overview band 1.1 MB with 21,632 features (0.6 MB with 11,621 before) and the file 65.8 MB. **Version 12** keeps only two kinds of administrative boundary: national borders (`admin_level=2`) and the level of states and counties (`admin_level=4`). Municipalities and the other levels (3, 5 to 10, and a boundary with no level) became `other`: their tags stay in the store and nothing draws them, because a thin dashed line every few kilometres made a national border look like any municipal border, and a runner does not need them. A national border in the sea (the Norway to Sweden border in the Idefjord is `admin_level=2` with `maritime=yes`) is a `countryBorder` too and gets the wide subdued band: before, every `maritime=yes` border was an ordinary boundary, so that border was thin; the limit of the territorial waters or of an economic zone (`border_type=territorial`, `eez`, `contiguous`) is not a border anyone crosses and is not drawn. Protected areas and national parks stay boundaries (until version 13). On the Halden and Svinesund area the file had 53 boundaries and 1 country border; it has 42 boundaries (protected areas and counties), 2 country borders and 5,347 `other`. **Version 13** (found in Fredrikstad) appends `waterEdge` (32), `parkBorder` (33), `parkBorderSea` (34) and `pier` (35). (1) A lake, a fjord or a wide river had no outline, while the sea had its coastline: the outline of every `waterArea` is now a line of its own, class `waterEdge` (not a stroke on the area, so that stretches can be left out), in the colour of the coastline. A stretch is left out where it lies within 6 m of a coastline (the coast draws it) or has water on both sides, tested 3 m to each side (the line where two water areas meet is no shore). (2) The coastline that closes the mouth of a river is mapped across the river's own water, with the river on the land side: a coastline stretch whose points 10 m and 20 m to the left (the land side) both lie in a water area is not stored as a coastline (the sea is built from the ways and is not affected). Testing 4 m left first dropped the banks too, because the outline of a river and the coastline along it are often mapped a few metres apart; two distances inland tell a mouth from a bank. (3) The centre line of a river or stream (`waterway=river`, `canal`, `stream`, `ditch`, `drain`; not dams and weirs) is left out where it lies in a water area, so no dark line runs through a wide river. All three tests sample the line every 25 m (`LineSplitter`) and cut at the sample where the answer changes, so a cut is within 12.5 m of the true change; the water areas are the closed ways and complete multipolygons of the extract (`AreaPolygons`, shared with `TownIndex`), indexes are built when first needed. (4) `parkBorder`: protected areas used to be `boundary` and were drawn like municipal borders. They are lines of their own class, dark green dashed, and the stretches in the sea are `parkBorderSea`, dark blue dashed: the builder now makes the sea first (`prepareSea`) and keeps a `SeaLookup` (the sea rings sorted into bands of latitude, a ray test against a few hundred edges), then splits the border at samples 25 m apart. Many protected areas are relations of type `boundary` whose ways carry no tags; they are assembled like multipolygons, and a member way that is itself a park border is not stored twice. `leisure=nature_reserve` counts. (5) `pier` (`man_made=pier`, `breakwater`, `groyne`) used to be a generic `poi` with no drawing: a marina was a patch of empty water; the standard style draws piers from zoom 14 as a grey line (or a filled area). The Watch copy has none of the four classes. A style file written before them has `parkBorder` and `parkBorderSea` drawn as `boundary`, and no outlines or piers. On Fredrikstad (8 km, 1,059 coastline ways): 323 water edges, 10 stretches of river centre lines dropped inside water areas (waterLine 880 to 857 features), 4 stretches of coastline at river mouths, 178 park borders on land and 119 in the sea (104 stretches), 732 piers (before: poi). On Oslo (15 km), rule table 12 against 13: build 10.74 s against 10.95 s, file 65.7 against 66.5 MB, peak memory of the build 467 against 454 MB (the sea is now kept until the end of the build, and the cut dominates); 2,640 water edges, 333 stretches of river centre line dropped, 8 coastline stretches at river mouths, 1,068 park borders on land and 594 in the sea, 2,316 piers. The same version fixes `LocalMetres` (above), which moved 56 of 27,613 footways in Oslo from `pavement` back to `path` (beside roads 3,710 to 3,645, in built-up areas 6,973 to 6,979). A closed line that is cut at its first vertex is joined again, so a ring does not get a break in its dashes where it starts. A way that two park relations share is still drawn once for each relation. **Version 14** gives the ways of national and state borders a name: a border way seldom has one, the names are on the relations of the two regions it separates, so the builder takes the `name` of every `type=boundary` relation (admin level 2 for a national border, level 4 for a state border; `BorderNames`) that has the way as a member, sorts them and joins them with an en dash (`Norge – Sverige`, `Akershus – Østfold`; the data does not say which region is on which side). A way with a name of its own keeps it. The name is stored as the feature's name only, not as a tag, so the stored tags still say what OSM says. The county relations a national border is also part of are not used for it. Only the name changes, so the file is the same size to within a few bytes; a store built with an older rule table has no border names (the viewer and `geomapkit render` already note an old rule table). **Version 15** puts each name on its side: the name of a border way is now the names of the regions on its left, a line feed and the names on its right, left and right looking along the way as it is stored (`SidedName`; a side with no region in the data is empty, several regions on a side are joined with ` / `), so a map can write each name on the side of its region. The data does not say which region is on which side, and the relations do not agree on a direction (the national relations of Norway and Sweden and the county of Finnmark run clockwise, the county of Østfold and the country of Liechtenstein counter-clockwise, found by following them in the Halden, Storskog and Liechtenstein extracts), so `BoundarySides` follows the ring of each relation: its outer ways in member order, each in the direction in which the ring runs through it (decided by the end nodes it shares with the next and the previous member), closed into one ring from the nodes; the sign of the area (planar, longitudes unrolled and scaled by the cosine of the mean latitude) says clockwise, where the region is on the right of the direction of travel, or counter-clockwise, and the direction of travel against the way's own direction swaps the side. A ring is only followed when at most 2% of the way members are missing from the extract and the direction is known for at least 90% of the outer ways; an incomplete relation is not guessed from a chord (tried on the Swiss relation, 630 ways missing: wrong). A region whose ring cannot be followed takes the side that the other region leaves free: in a Norway extract the relation of Sweden has more than half of its ways missing, and the ring of Norway (1 of 229 ways missing) decides for both. If neither can be followed the old text, the names in alphabetical order joined with an en dash, stays and is written above the line. On Halden the names of the Idefjord and of the border south of it are on the right sides (Norge on the Norwegian side, Sverige on the Swedish side). **Version 16** draws the agreed line between two countries in the sea. It is tagged `border_type=territorial` like the limit of the territorial waters, which is not drawn, so the Norway to Sweden line ended where the Iddefjord opens (59.08 N, 11.15 E on Halden) and the rest of it, out to the Skagerrak, was missing. The two are told apart by the relations: the line between two countries is a member of the national relations (level 2) of both, a limit of the waters of one country only of that country's (checked on Norway: 1 of the 20 first `territorial` ways near Halden is in two relations, the line to Sweden; all others, from Svalbard to the Skagerrak coast, in one). A sea-limit way in two national relations is classified as `countryBorder` as if it had no `border_type` (`BorderNames.countryRelationCount`); the other limits stay `other`. On the Halden area the file has 28 country borders. **Version 17** gives military land (`landuse=military`) a class of its own, `militaryArea` (36), overview band, not on the Watch. It was part of `landuseUrban` and was drawn as grey urban land, which made radar sectors and firing ranges in the Stockholm archipelago look like grey fans in the sea. These are areas to keep out of, so the standard style draws them with a dashed red outline and a faint red tint (alpha 26 of 255), from zoom 9, on layer 16, above the water (13), the buildings and the shore lines (14), and below the roads (20 and up): the tint is translucent, so a military area at sea shows the sea under it and one on land shows the land, without a test of whether the area lies in water. `TownIndex` still counts it as built-up for the footway rule, as before; a style file written before the class existed draws it like `landuseUrban`. Both fans in the Stockholm archipelago (a radar sector and a firing range, `military=range`) are `landuse=military` and render as outlines in the sea; other military tags (`military=*` without `landuse=military`) are not classified yet, and the Watch has no marking of military land (a possible later change: an outline only). Files built with version 16 or older need a rebuild to get the class. Order: peak, place, anchors (`amenity` drinking water, shelter, toilets; `natural=spring`; `tourism` huts and viewpoint), highway, railway, power, aerialway, piste, waterway, water areas, forest, tree, boundary, land cover, urban land use, building, barrier, transport stop, road point, other POI keys, `other`. A `piste:type` way that is also a highway stays a path or track. Anchors come before `building`, so a hut tagged as a building is a hut. Nodes are points, open ways lines, assembled multipolygons areas. A closed way is an area if it has `area=yes`, or an area key (`building`, `landuse`, `leisure`, `amenity`, `tourism`, `shop`, `historic`, `aeroway`, `place`, most `natural` and `man_made` values, `waterway=riverbank`), unless it also has `highway`, `railway` or `barrier` (then a line) or `area=no`. The subclass byte holds the specific value in its low six bits (the `highway` value, the `tracktype` grade for tracks, and so on), bit 6 for a bridge and bit 7 for a tunnel. A band is the lowest band a feature is stored in; it is also stored in the bands above it, so a mid-band feature is in mid and detail. Bands are fixed per rule, not by feature size. **Version 18** (2026-11-09) splits the ground that is not vegetation off `landcover`: `glacier` (37), `bareGround` (38), `wetland` (39) and `sand` (40) are classes of their own, so that a glacier is white, sand light yellow and a boulder field grey and not a lawn (a runner reads the land cover of a mountain from it), and `natural` rock, bedrock, blockfield and shale and `landuse` cemetery, brownfield, greenfield and pasture are classified (counted over the 163 blocks of Østlandet and Sweden, as objects of any kind, areas, lines and points, they were unclassified: `rock` 6,990, `cemetery` 1,482, `brownfield` 570, `greenfield` 331, `blockfield` 18). **A node with one of these tags is not stored as a land cover class** (they are surfaces, a node has nothing to draw): measured on four mountain blocks, 47 of the 77 `natural=rock` objects, 80 `wetland` objects and 18 `glacier` objects were nodes; they stay unclassified points with their tags. Rock, bedrock, blockfield and shale start at the mid band because they are mostly small patches. Left out on purpose: `landfill` (838), `animal_keeping`, `plant_nursery`, `winter_sports` and the `landcover=*` tag (not measured), and `natural=hill`, `stone`, `bay`, `cape`, `valley` and `ridge`, which are points, names or lines. **Version 19** (2026-11-09) keeps all the rest of the land use: every `landuse` value that no rule takes, and `natural` dune, moor, tundra and bog, are the class `landUse` (41) and not unclassified objects. The standard style draws nothing for it, so the default map does not change; the point is that the data is kept in a form a style can use (a livestock map from `animal_keeping`, `pasture`, `meadow`, a map of landfills and nurseries). The class is stored from the mid band, and the value of the `landuse` or `natural` tag (only that tag) is stored in every band it is in, not in the detail band only: the cell codec writes the tags a feature has in every band, and the builder gives all tags in the detail band and only that value elsewhere (every feature already has a tag count, so the layout and the format version do not change). An object with `landuse` and an address only was `address` and is now `landUse`. A footway inside a `landUse` area (church grounds, a school) counts neither as built-up nor as green for the sidewalk rule, as when it was unclassified; whether `education`, `religious` and `institutional` should count as built-up is left open. The rules are the last of the surfaces: an object that is also a building, a shop or a hut keeps that class, and only an address-only object ranks below. Nodes with these tags stay unclassified points. The coarse levels (question 50) hold the classes a style shows at their zoom, so `landUse` is not in them until a style shows it, and they do not carry its tag. Selecting by value in a style (a fill or border for one class and one value) is the next step and not built. The same version puts `sand`, `bareGround` and `wetland` on the layer of the forest, above it, so that open sand between woods (inland dunes), rock outcrops and bogs are not hidden by a forest polygon that covers them. A style file from before version 18 draws the three new classes like `landcover`; stores built with an older table must be rebuilt to get them (`mapviewer` says so). **Version 20** (2026-11-09) keeps the names of wide rivers: the builder drops the centre line of a river (`waterway=river`, and canals and streams) where it lies in a water area, and the area (a `riverbank`) is mostly unnamed, so the name was lost; the dropped stretches of a way that has a `name` are now stored as `riverName` lines (class 42, overview band, no stroke in any style, not on the Watch), and `BuildReport.riverNameStretches` counts them.

**Overlay classes (2026-11-10).** The first match of the rule table is the *primary* class, and one object has one of them. Some classes can be had as well, and for these the single class lost information that the map needs: a stream that the national border follows was only a stream (half of the Irish border, 408 ways tagged both, and 59 more with `admin_level=2 boundary_type=nation` and a `waterway`), a forest that is a nature reserve was only a forest (the reserve border was not drawn), a track with `piste:type` was only a track. `FeatureClassifier.overlays(_:primary:)` gives the overlay classes of an object: the border of a country or a state (`countryBorder`, `boundary`), the border of a protected area (`parkBorder`) and `piste`. Each group of tags (`boundary`, `admin_level` and `border_type`; `boundary` and `leisure`; `piste:type`) is classified alone, so the levels of the borders and the limits of the territorial waters work as for an object that has only those tags. The builder stores the overlay as a line feature of its own, on the whole way (or on the rings of a multipolygon, for the reserve border), next to the primary feature, with the same object ID. A way that is a member of a national or a state border relation is a border whatever else it is, unless it is tagged as a limit of an area of sea. **Other classes are not line overlays, for different reasons.** The survey of the Belgian file (11.5 million ways, 5.2 million with two or more matching classes) and of the Danish file (6.8 million, 0.6 million) showed that the overlaps are almost all four classes next to another class. `landUse` is matched by the same `landuse` tag that gives the primary class (`landuse=grass` is `landcover` and `landUse`), so it is the same information. `address` has no style, so nothing is drawn for it (the house number stays in the raw tags of the building). `roadPoint` (a crossing or traffic calming on a street) has a point style only and is a line on a way. **`poi` on an area was a real gap, and is a different kind of overlay (built 2026-11-10):** a shop, a church or a hut that is mapped as an outline (about 26,000 buildings in Belgium and 31,000 in Denmark) is a `building`; the renderer draws the dot and the name of `poi`, `poiAnchor` and `transportStop` for point features only, and an area gets a name only if its own class has a label style (`waterArea` has; `building` and the land cover classes have not), so such a building had no marker and no name. `FeatureClassifier.pointClass(_:)` gives the first point class of the rule table in the tags of an area, whatever class comes before it, and `FeatureStoreBuilder.storeAreaPoint` stores a point of that class at the pole of inaccessibility of the area (`PolygonPole`, the point farthest from the edges, by Mapbox's polylabel, in the stored coordinates with the longitude scaled for the latitude; for a multipolygon in its largest polygon). A `poi` gets its point only if the area has a name (a parking lot or a pitch with no name would be a dot with nothing to say); a `poiAnchor` (hut, shelter, viewpoint) and a `transportStop` (station) get it whether it has a name or not; a `waterArea` gets none, since its name is written in the water. Checked on the centre of Leuven (Belgian file, zoom 17): Sint-Pieterskerk, the M-Museum, HEMA, Tafelrond, Volksbank van Leuven and Galleria Inno now have their name and dot. The rule table stays 21 and the blocks need a rebuild. Not covered: `place` and `peak` outlines (an island mapped as a place outline keeps its name from its place node), and a marker for an area with a node of its own (the node and the point are then both stored: a few duplicates). New overlays are added to `overlayGroups` when a case turns up. The rule table version stays 21: no primary class changes, what is stored changes, and the blocks need a rebuild.

**Sea (decided and implemented, rule table version 5).** OSM has no sea polygon, only coastline ways. `FeatureStoreBuilder` joins them in their own direction (`CoastlineJoiner`; a coastline way is never reversed to fit) and `SeaBuilder` clips the joined lines to the block of written cells and builds the sea inside it: each piece enters the block at one point and leaves it at another, and walking the block border clockwise from a leaving point to the next entering point stays in the water, so the pieces and the border stretches between them close into sea polygons. A closed coastline that runs counter-clockwise (land inside) and lies in water is an island, cut out of the sea as a hole (even-odd fill); one that crosses the border is joined into the walk like any other piece; a clockwise ring is water inside. A block that no coastline crosses but that has islands is open sea. The polygon is one `sea` area feature. It is built again for every cell and band (`SeaBuilder.parts(in:lines:sea:)`) from the coastline pieces in that cell, using the coastlines simplified for the band, so each stored part is a real polygon bounded by coastline and cell border; a cell with no coastline is the cell square if the whole-block sea contains its centre, and nothing otherwise. A block with no coastline at all gets no sea from this, so in a block set the producer adds the sea of open-sea blocks afterwards (question 53). Cutting the whole sea ring and the islands to cells instead gave an outer square and a hole sharing edges on every cell border, and the renderer showed a faint grid on land where anti-aliasing does not cancel them (found in Lofoten). The generic rule that two squares covering a cell cancel under even-odd is also applied when storing any area (`FeatureEmitter.withoutCancellingSquares`), which keeps lakes with big islands small. **Gaps and the country border:** a coastline that starts or ends inside the stored block cannot say where the water goes next. That is the normal case where the extract stops at a country border (the shore on the other side is not in the file), and also a way that is broken in the middle. `CoastlineGaps` (run before the sea is built, on the joined coastlines) repairs it in two steps. First the end of a coastline is joined to the nearest start of one (its own included) with a straight line, shortest first, if the gap is at most 20 km, the line crosses no coastline, and a coastline closed on itself encloses at least 5% of the square of its gap (so a dangling stub is not closed into a sliver); the sea then runs up to the line, which stands for the border (a coast with the land inside becomes an island, one with the water inside a lake of water). Second, a loose end that finds no partner but lies within 1.5 km of a country border way of the extract (`boundary=administrative`, `admin_level=2`, maritime or not: the extract is cut along a polygon that follows the border to within a kilometre or so, the unpaired end near Halden was 830 m from the border) is carried straight on, in the direction of its last 50 m, to beyond the edge of the block, so the sea runs on to the edge; a loose end that is not at a border is a broken coastline and stays loose. A coastline way with a node missing from the extract is left out (counted) and its gap is repaired the same way, so one broken way far from the area no longer stops the sea. On the Halden and Svinesund area (15 km, the Swedish border through the Idefjord and the Oslofjord): before, the build printed the warning and had no sea; now 1 gap of 3,490 m is closed, 1 end is carried to the edge, and the sea has 5 polygons and 1,078 islands, with the Swedish side left empty; Oslo and Lofoten, which have no gaps, are byte for byte the same. **Limits:** (1) a loose end that is not at a border, or whose line would cross a coastline, or whose gap is above 20 km, is not repaired; then no sea is built at all and `geomapkit build` prints a warning with the count; (2) a coastline way with no vertex inside the cut area is not in the extract (question 31), so a block crossed only by such a way is taken for land; (3) the cost: the coastline segments are sorted into the cells they touch once per band (`SeaCellBuckets`), so each cell sees only its own segments, and the cells with no coastline near them are sea or land in connected groups, one point test per group (`SeaBuilder.parts(lines:sea:columns:rows:zoom:)`); a first version clipped every segment against every cell, which took about 9.5 s more than a build without the sea on a 160 km box of the Lofoten coast (26,161 coastline ways, 8,010 cells) and is now about 2 s (build 27 s to 19.7 s, the rest being the rest of the build); the output has the same shapes in every cell, checked against the slow way on the real file and on random islands and coasts in a test, differing only in the order of the parts and the starting vertex of a ring in 21 of 8,010 cells; Oslo, 15 km, 346 coastline ways, 2 sea polygons and 227 islands, added no measurable time to the 7 s build. A lake mapped with `natural=coastline` is not handled specially.

### Clipping and simplification (decided, `FeatureStoreBuilder`)

- **Order:** a feature is simplified per band as a whole, then clipped to cells; the detail band is never simplified.
- **Space:** intersections are computed in Web Mercator in `Double` (x is longitude in 1e-7 degrees, y the projected latitude), because a segment is straight on the screen in Mercator and not in latitude/longitude. Only the final vertices are rounded to 1e-7 degrees.
- **Cell borders** are integers in 1e-7 degrees from one rounding function, so two neighbours share the same integer. A cell is closed: a vertex exactly on a border belongs to both cells.
- **Seams:** a border point is computed from the original segment and the border with the segment's end points in a fixed order, so both neighbours get the same point, apart from a rare rounding tie of one unit (1e-7 degrees, about 1 cm). The tests allow one unit.
- **Lines:** clipped per segment (Liang–Barsky). A line that leaves and re-enters gives several pieces, each with its own offset. `continuesBefore` and `continuesAfter` are set when the piece does not begin or end at the first or last vertex of the line. A piece that is a single point is dropped, and a piece lying along the east or south border belongs to the neighbouring cell. The offset is the cumulative haversine distance in centimetres to the piece's first vertex.
- **Rings:** Sutherland–Hodgman, with each edge tracked as real or artificial: the edge that joins a point where the ring leaves the cell to the next point where it returns is artificial; fragments of real edges stay real. A ring that covers the cell becomes the cell's square, all artificial. A result with zero area is dropped. Fill uses the even-odd rule, so a hole that covers the cell cancels the outer ring.
- **Simplification:** Douglas–Peucker in Web Mercator; tolerance 0.5 pixel of a 256-pixel tile at the highest zoom of the band (about 38 m for overview at zoom 11 and 4.8 m for mid at zoom 14 at the equator, smaller on the ground at higher latitudes). End points are kept; a ring keeps at least three distinct vertices or is dropped from that band. Neighbouring polygons are simplified independently, so a shared border can open a small gap in the overview and mid bands, and a simplified ring can cross itself in rare cases. Measure on real data before adding shared-border simplification.
- **Not supported:** the antimeridian. **Cost:** every cell in a feature's bounding box is clipped separately, which is quadratic for very large polygons; measure on the end-to-end data and add a strip-wise pre-clip if needed.

### Multipolygon assembly (decided, `FeatureStoreBuilder`)

- **Scope:** only `type=multipolygon` relations are assembled. Boundary and route relations stay in the relation table only; assembled route lines are deferred.
- **Rings:** outer and inner way members are joined separately, end to end by shared node ID (ways reversed as needed; a closed way is a ring by itself). Role `outer` and an empty role are outer rings, `inner` is a hole, other roles and non-way members are ignored. Where several unused ways meet at a node the lowest way ID is taken, so the result does not depend on the order of the members; if that leaves a chain open, the relation is incomplete. Ways join by node ID, not by position, so two ways that end at different nodes with identical coordinates do not join.
- **Holes:** each inner ring goes to the smallest outer ring that contains most of a sample of its vertices (at most five, shared vertices ignored, and the bounding boxes must nest, so many holes in a large outer ring stay cheap). An island inside a hole is its own outer ring. Outer rings are normalized counter-clockwise and inner rings clockwise in Web Mercator; fill with the even-odd rule.
- **Incomplete (all or nothing):** a relation is incomplete if the extract flags it, a member way or node is missing, any ring does not close, or there is no usable outer ring. It then produces no polygon. Its rings and chains come out as **line features** (object type relation, the relation ID, class from the relation's tags, flag `incomplete`), clipped like lines with continuation flags and offsets; the renderer draws an outline and never fills.
- **Tags:** the classifier gets the relation's tags without `type`. Old style: if the relation has no tags besides `type` and exactly one outer way, the way's tags are used and that way is not emitted a second time. Untagged member ways are not emitted separately; their geometry is in the area and their IDs in the relation's member list. Tagged member ways are emitted normally.
- **Counted, not repaired:** an assembly report counts unclosed chains, rings without area or with fewer than four points, inner rings that no outer ring contains (ignored, the polygons stay valid), missing members and duplicate members. **Self-intersections are not detected** (a check is O(n^2) per ring, too slow for coastline-sized rings), so a self-intersecting ring is filled even-odd; this replaces the earlier idea that the report counts them.

### Store builder (decided, `FeatureStoreBuilder.build(from:)`)

- **Cells written:** only the cells that lie fully inside the extract's bounding box (a rectangle of columns and rows), because the extract is incomplete near its edge. Pieces that fall in other cells are dropped and counted (`piecesOutsideCells`). A box smaller than one cell gives an empty, valid store. The file's bounding box is that of the written cells. A cell owns its west and north border, not its east and south border, which also decides where a point or a piece lying along a border goes.
- **What is stored:** every tagged node as a point (untagged nodes only as way vertices), every way as a line or area with all its tags, every relation in the relation table (all types, tags and members, `isIncomplete` mirrors the extract's flag). A feature is stored in its lowest band and every band above it; tags only in the detail band, the `name` value in all bands. Untagged ways that are members of a multipolygon are not stored separately, and a single outer way whose tags a tag-less multipolygon adopts is not stored twice; untagged ways in no relation are stored as `other` lines. A way with a node missing from the extract is split at the gap (the pieces are counted in `waysWithMissingNodes`), never drawn across it. Consecutive duplicate vertices are merged.
- **Multipolygons:** assembled as described above; incomplete ones become line features of the relation's class with the `incomplete` flag (clipped as lines, with continuation flags and offsets).
- **Watch copy (`BuildProfile.watch`, provisional):** only classes with the Watch flag, bands mid and detail only, only the `name` tag, and no relation table. The writer drops strings that nothing uses, so the Watch copy carries a pruned string table. The corridor cut for the Watch may refine this.
- **Reporting:** `BuildReport` counts what was stored, suppressed and skipped; `FeatureStoreFile.statistics()` gives sizes and counts per band and class for measurements. Builds are deterministic.
- **Cost:** the whole result is held in memory (one writer per block of cells), single-threaded, with cancellation checks.
- **Measured on the real Liechtenstein extract** (Geofabrik, 2026-11-05, 3.50 MB, centre 47.14 N 9.52 E; release build on a Mac, one run each, warm file cache). 10 km radius: the cut gives 330,704 nodes, 38,335 ways and 954 relations (13.2 MB as an extract, cut 0.25 s). The **full store** takes 0.37 s to build and is 3.93 MB in 22 cells: overview 57 KB (1,012 features), mid 661 KB (12,732), detail 2,552 KB (48,869), about 52 bytes per feature in every band; string table 222 KB (11,121 strings), relation table 441 KB. That is 112 % of the compressed source file and 30 % of the extract's memory. The **Watch copy** takes 0.24 s and is 1.66 MB (47 % of the source): mid 599 KB (12,230 features), detail 1,050 KB (16,095), string table 15 KB. 15 km radius (this covers the whole country): 358,093 nodes, 42,120 ways, 1,030 relations; full store 5.04 MB in 41 cells, Watch copy 2.20 MB in 35 cells. Opening a file takes no measurable time, `verify()` 10 to 30 ms, and reading the busiest cell (8,813 detail features) takes 2.0 ms for the detail band and 0.3 to 0.5 ms for the mid band (0.5 ms for the Watch copy's detail band). The numbers answer question 36 for this region: a lossless store of a 15 km area is about 5 MB, and the Watch copy about 2 MB. Other regions are denser (Oslo has about 12 times the nodes), so repeat the measurement there before setting a Watch ceiling (question 39, 43).
- **Content checks on the same data** (`LiechtensteinEndToEndTests`, skipped unless `GEOMAPKIT_LIECHTENSTEIN_PBF` points to the file): every relation (tags, members, roles) and every tagged node is in the file byte for byte; for 31,215 ways the tags, class and every vertex inside the written cells are stored, and the 13,340 lines and 17,519 areas that lie wholly inside keep their length (within 0.5 m) and area (within 2 cm times the perimeter; the rounding of a cut's two border points to 1e-7 degrees, about 1 cm, makes the area error absolute); the 205 assembled multipolygons wholly inside (180 of them with holes) keep their area; the 2 incomplete ones are outlines only; the Watch copy is a subset; builds are deterministic.
- **Observation for the style:** with rule table version 1 about a third of the stored features had class `other` (individual trees, crossings, bus stops, fences and walls); version 2 splits them out, see question 47. The numbers above are from version 1; with version 2 the full store is 3.94 MB and the Watch copy 1.69 MB at 10 km, 5.05 MB and 2.23 MB at 15 km.

### Map style (decided, `MapStyle`)

- **A style is Swift data, keyed by class.** `MapStyle` holds a background colour and a `ClassStyle` per `FeatureClass`; it never looks at raw tags. A class without an entry is hidden, which is how the Watch style leaves classes out. `MapStyle.standard` (iOS, iPadOS, macOS) styles every class except `other` and `address`; `MapStyle.watch` styles the Watch profile only, from zoom 12, with thicker lines, no dashes, a road outline only when zoomed in, and labels only for places.
- **Zoom-dependent values** are `ZoomValue<T>`: stops over fractional zoom, linear interpolation, constant outside the first and last stop. It works for numbers and for `MapColor` (sRGB, no SwiftUI or Core Graphics dependency, so the target builds everywhere).
- **A `ClassStyle`** has an optional fill (areas), stroke (lines and area outlines, with casing, dash, cap and join), point symbol and label, a `visibleZoom` range on top of the store's bands, and a `layer` for drawing order (lowest first; trails are above roads). `visibleClassIDs(atZoom:)` gives the set for `FeatureStoreFile.features(in:band:classes:)`, so hidden classes are skipped without decoding.
- **Road width from `lanes` (decided).** `LineWidth` is a legible screen width by zoom (`points`, also the minimum) plus an optional `GroundWidth` (metres per lane, default lanes, a cap). The renderer passes the zoom, the metres per point at the current latitude and the feature's `lanes` tag; the width is `max(points, lanes × metresPerLane / metresPerPoint)`. Zoomed out, every road keeps its legible width; zoomed in, a four-lane road is drawn twice as wide as a two-lane road. Untagged or invalid `lanes` (below 1) use the default (2); values above 12 are capped. `lanes` is the only tag the renderer reads for drawing, and it is available in the detail band only (tags are stored there); other bands use the default. Roads (`roadMajor`, `roadMinor`) get a `GroundWidth` and a casing (outline): the renderer strokes the casing at `width + 2 × extra` first and the fill on top, so a zoomed-in motorway shows as a fill with an outline. **Crossings at the same level:** road classes put their casing on a shared `casingLayer` below all their fills, and `MapStyle.drawSteps(atZoom:)` returns casing steps before body steps, so the renderer draws every outline first and every fill after; at a crossing the fills run through each other's outlines and the outlines join. The renderer does the same inside one class (all casings of the class, then all strokes). Bridges and tunnels are drawn as their own groups (see "Bridges and tunnels" below); the extra width is a `ZoomValue` that grows with zoom (0 means no outline); paths and tracks keep screen widths. A `width` tag in metres and one-way lane splitting are not used yet.
- **Style file (decided, format version 1).** A style can be read from and written to JSON of our own (`MapStyle(json:)`, `jsonData()`), so custom styles need no recompiling. Start from `geomapkit style standard --output my.json`, edit, then `geomapkit render … --style my.json`. A file without a `countryBorder` class uses its `boundary` style for national borders, so styles written before that class existed keep their borders. The format mirrors the model:
  - Root keys: `formatVersion` (must be 1), `name`, `background`, optional `attribution` (`full` | `compact` | `hidden`) and `classes`, an object keyed by the `FeatureClass` case name (`roadMajor`, `waterArea`, …). A class that is missing is hidden.
  - A class has `layer` (required, an integer from 0 to 99, because bridges are drawn 100 layers above their class) and optional `visibleZoom` (`[lowest, highest]`, default `[0, 24]`), `casingLayer`, `fill`, `stroke`, `point`, `label`, `bridge` and `tunnel` (see "Bridges and tunnels"). `fill` has `color`; `stroke` has `color`, `width` (`points` and optional `ground` with `metresPerLane`, `defaultLanes`, optional `maximumLanes`), optional `dash`, `cap` (`butt`|`round`|`square`), `join` (`miter`|`round`|`bevel`) and `casing` (`color`, `extraPoints`); `point` has `radius`, `color`, optional `outlineColor` and `outlineWidth`; `label` has `size`, `color`, optional `haloColor`, `haloWidth`, `priority`, `visibleZoom` and `placement` (`onLine`, the default, or `besideLine` for the names of borders; it is written only when it is `besideLine`, so a file without such labels is the same as before, and a file with them is refused by a reader that does not know the key).
  - **Amount of text:** the optional root key `labels` has `padding` (clear space around each label in points, default 2; larger gives fewer labels) and `maximumCount` (most labels per view, default none; the highest priority labels stay). A label also has its own `visibleZoom` (`[lowest, highest]`, default `[0, 24]`), so a name can appear later than its shape. Removing a class's `label`, its `size` and its `priority` remain the per-class controls. The Watch style uses padding 6 and at most 6 labels.
  - Colours are `"#RRGGBB"` or `"#RRGGBBAA"` (8 bits per component). A zoom-dependent value is one value (same at every zoom) or a list of `[zoom, value]` stops, for example `[[12, 1.5], [16, 3]]`.
  - **Strict reading:** unknown keys and unknown class names, a wrong version, bad colours, empty stop lists and negative or non-finite numbers are errors (`MapStyleError`) that name the place in the file, so a typo cannot silently fall back to a default. Output is deterministic (sorted keys). A layout change bumps `formatVersion`.
  - The attribution setting travels with the style; a style file with `hidden` makes the app responsible for the credit (see "Drawing backend").
- **Not decided yet:** a MapLibre style subset as a second external format (question 15); only worth it if styles need to be shared with other tools.

### Map scene (decided, `MapRender`, part 1)

`MapRender` is built in two parts: first a scene with no graphics dependency, then the drawing backends.

- **`MapViewport`:** centre, fractional zoom and size in points. Web Mercator with 256-point tiles (the world is `256 × 2^zoom` points wide), with a bearing: the compass direction at the top, in degrees clockwise from north, 0 up to 360 (0 is north up). The turn is part of the projection (offsets from the centre are rotated in `Double`), so scene building, clipping and label placement, which work on screen points, are unchanged; `cells` uses the bounding box of the turned view, so at 45° about twice as many cells are read. See "Map rotation" in section 7. Screen positions are computed relative to the centre in `Double`. It gives `metresPerPoint` at the centre latitude (for the `lanes` road width) and the storage cells that touch the view, with a margin. Views over the antimeridian are not supported (columns are clamped, not wrapped).
- **Band choice:** below zoom 12 overview, 12 to below 15 mid, 15 and up detail (the provisional boundaries). If the file lacks the band (the Watch has no overview), the nearest finer band is used, then the nearest coarser. Above the detail band the detail geometry is scaled (overzoom); there is nothing to decode extra.
- **`MapSceneBuilder` / `MapScene`:** reads only the cells in view, one band and the classes the style shows (the others are skipped by length in the file), joins line pieces, projects, culls and returns the steps in `MapStyle.drawSteps` order. It is rebuilt when position or zoom changes; on the Watch the app decides when (see Battery). The scene is plain `Sendable` data, so tests need no graphics context and any backend can draw it.
- **Joining clipped lines (decided):** pieces of one way join when the first has `continuesAfter`, the second `continuesBefore`, and the end vertices are within 3 units of 1e-7 degree (about 3 cm; each cell rounds its own clip point). The order is the stored `offsetAlongLine`. A line that leaves and re-enters a cell stays two lines. Areas are not joined: each cell's piece is filled on its own, and its outline leaves out the artificial (cell-border) edges, merging a run that wraps around the ring start.
- **Tags read for drawing:** `lanes` (detail band only) and `name`. Nothing else.
- **Divided roads (decided, `MapRender`, no data rebuild).** Where a road divides into two carriageways, each is a one-way way with its own `lanes` tag, and the divider showed as a gap in the road, so the pair looked narrower than the undivided road it came from (found at Nydalen, Oslo). `DividedRoads` finds the pairs in the scene and `SceneMedian` is the strip between them, filled in the road's colour in the body step of the class, so the two carriageways and the divider read as one wide road with one outline (the casings of the sides stay, those between them are covered). A divider line, in the colour of the road's outline (the bridge outline on a bridge, at least 0.6 points wide), runs along the middle of the whole strip: two carriageways are separated by something, so a pair without a divider line would not be a pair. **What is a pair.** Two lines of the same class (`roadMajor` or `roadMinor`) and structure (ground or bridge), both one-way (`oneway` yes, true, 1, or -1 for against the vertices; not a roundabout, which wins over the `oneway` tag in any tag order), flowing in opposite directions (within 25 degrees of straight against each other), and not named differently (two names that differ are two roads; a way without a name may be half of a named road). Samples are taken every 3 points along the line with the lower index of the two; the nearest carriageway beside the sample (not past its end), with the edges at most 6 m apart, is the match. The matches in a row are then judged as one stretch, not sample by sample (a first version decided every sample against 6 m, so a road whose gap hovered around 6 m was merged in pieces, and two different roads that came within 6 m were merged): the middle value of the gap between the edges must be 1 to 4 m (nearer, they touch or overlap and are one road drawn twice or a merge; further, the divider is wide enough for two roads), the ends of the stretch whose gap differs from the middle value by more than 1.5 m are cut off (the merge or fork at the end of a divided road stays as two roads), what is left must vary by at most 2 m and be at least 20 m long (shorter ones are the ends of ways that meet at a junction: at Nydalen they were stubs of 5 and 13 points). Measured on Oslo before the stretch rule, the strips at the roundabouts of Nydalen had a gap from -2.6 to 6 m (carriageways merging), and the pair at Lybekkergata one of 5.9 to 6.0 m. The `oneway` tag is in the detail band only, so the other bands and the Watch copy have no strip (nothing is done there: the Watch finds no candidate and returns at once); tunnels have none. **Limits:** a street that crosses the gap is hidden under the strip, because the strip is drawn at the layer of the class (a major road's strip over a minor street), so the street seems to end at each edge; a style whose road colour is translucent gets no strip (a translucent fill would be blended twice where it overlaps the bodies), so the gap shows; a motorway that carries no `oneway` tag is one-way by OSM's rules but is not paired here, because the scene knows the class and not the `highway` value; a pair whose gap widens along its length (a slow fork) is two roads. Cost: the segments of the one-way roads in the view are put in a grid (`CarriagewayGrid`), and each sample looks at the cells next to it; the scene of a 1000 by 800 view of central Oslo takes 0.05 s at zoom 15 and 0.02 s at zoom 17, the same as before (three runs each, rounded to 10 ms by the tool).
- **Bridges and tunnels (decided, `MapStyle`, `MapRender`).** The builder stores them in two bits of the subclass byte of every line (bridge `bridge=*` except `no`, tunnel `tunnel=*` except `no`), in every band, for paths, pavement, tracks, roads, railways and water lines. `Structure(subclass:)` reads them and `SceneLine.structure` carries them into the scene. A class opts in with `ClassStyle.bridge` (`BridgeStyle`: a casing, colour and extra width by zoom, drawn instead of the class's own casing) and `ClassStyle.tunnel` (`TunnelStyle`: an opacity factor and an optional dash). A class without them draws its bridges and tunnels on the ground like any other line. `MapStyle.drawSteps(atZoom:)` then adds steps with a `structure`: bridge steps (casing, then body) on the class layers plus `bridgeLayerOffset` (100), so every bridge is drawn after every line on the ground, and a tunnel body step on layer `tunnelLayer` (15), above the area fills (up to 14) and below the lines on the ground (20 and up); the steps on the ground draw only the lines on the ground. A tunnel has no casing, and is drawn fainter and dashed, so what runs over it stays on top. Both are drawn with flat ends (`LineCap.butt`, whatever the class uses): with round caps a bridge casing would thicken the ends of the deck as well as its sides, and a road would leave a tunnel with a round cap instead of a clean cut. The scene builder splits the lines of a class between these steps; the renderer asks `ClassStyle.stroke(for:)` for the stroke of a step. The standard style gives bridges a dark grey casing (roads 1.8 points wider at zoom 16, paths, tracks and railways narrower) and tunnels half or less opacity (roads dashed 5 on 3 off, rails 2 on 3, culverts 3 on 2); the Watch style has none, to keep its steps few. A line on the ground that starts or ends exactly where a bridge or a tunnel starts or ends (the same stored point) is marked `flatStart` or `flatEnd` by the scene builder, and the renderer strokes it with a flat cap at that end and draws the round cap of the other end as a circle, so a road comes out of a tunnel mouth, or onto a bridge, with a clean cut and its junctions elsewhere stay filled; a dashed line is only given flat ends. The same applies to a road (a class with a ground width) that ends at a vertex in the middle of another road, a T junction: it ends flat at the side of the through road instead of poking out of it with a round cap when it is wider. A through road that is cut into two ways at the junction is found too: where three or more road ends meet at a node and two of them leave in nearly opposite directions (the halves), every other end there ends flat, unless it leaves within 35 degrees of one of the halves (a fork, which keeps its round end so the wedge between the arms stays filled). A road that ends at the end of another road, or in the open, keeps its round end, and so do paths. **Width blend:** where one road continues into another road of the same class with a different width (a different `lanes` tag: a road divides into carriageways, a lane ends before a bridge), the step in width is blended. `RoadTaper` (`MapRender`) pairs the ends that meet at the same stored point and leave in nearly opposite directions (more than 140 degrees apart, so a side road is not a continuation), and sets `SceneLine.startWidth` or `endWidth` to the mean of the two widths when they differ by at least 0.75 points; both ways agree at the node. The renderer then strokes the first or last stretch of such a line, about 15 m long and at most 45% of the line, in 3-point pieces whose width changes linearly from that width to the line's own, each running 0.75 points into its neighbours so anti-aliasing leaves no seam, with the casing following the same widths; the ends that are not flat get their round cap as a circle of the width they have, unless the stroke has flat caps (a bridge or a tunnel, whose ends stay flat even where it blends to its neighbour). Dashed lines and lines of other classes are not blended, and only the detail band of a full store has `lanes` (the Watch copy carries no tags), so lower bands and the Watch copy show no blend. **Limits:** the order of two bridges that cross each other follows the class layer, not the `layer` tag (it is in the detail band only, and there are no stacked bridges in the sample areas); a bridge deck is drawn over point symbols on the ground; a bridge of a sidewalk is not distinguished. The style file takes `bridge` (`casing`) and `tunnel` (`opacity` 0 to 1, default 0.5, and `dash`) per class, read strictly like the rest.
- **Rotation (done):** see section 7.

### Drawing backend (decided, `MapRender`, part 2)

- **`MapRenderer`** is a protocol with one method, `draw(_:style:into:)`, and an associated `Target`. Everything that depends on data or style (decoding, band choice, joining, culling, ordering, label placement) happens before it, so another backend (Metal, SwiftUI `Canvas`) only has to turn steps into drawing calls. `CoreGraphicsRenderer` (target `CGContext`, screen points with the origin top-left and y down) is the first backend and the only one that uses Core Graphics and Core Text; it builds for all four platforms. A SwiftUI `Canvas` view can call it with the `CGContext` it gets from `Canvas`.
- **Drawing order:** background, then each `SceneStep` in order (casings first, so outlines of crossing roads join), then labels on top.
- **Areas:** filled with the even-odd rule (holes stay empty); an incomplete area is not filled, only outlined. A fill without outline gets a 0.5 pt hairline in the fill colour when it is opaque, which closes the seams between the pieces of neighbouring cells. The outline strokes real edges only.
- **Labels (decided for v1):** Core Text, Helvetica, halo as a wider stroke under the fill. `LabelCandidates` collects named points and areas that have a label style (`collect`) and named lines (`collectLines`); `LabelPlacer` places them greedily by priority (then OSM ID, so the result is deterministic): points try right, left, above and below the symbol, areas are centred. A label must lie wholly in the view and may not overlap another label or any point symbol; otherwise it is dropped. One label per feature for points and areas (the largest piece of an area wins). **Labels along lines (decided, `MapRender`, no data change except border names).** A name written along a road, a path, a river or a border: roads and paths from the street name, a border from the names of the regions on its two sides (rule tables 14 and 15). The line is cut to the part inside the view (`LabelPath.runs`). On each part the name is tried in the middle first, then shifted by a third of its length up to three times to either side, and on a part longer than 300 points or four name lengths again at that distance to either side, at most 8 times per part, so a long street carries its name more than once and a bend in the middle does not lose the label. A try is accepted when: the stretch under the name is straight enough (no segment turns more than 40 degrees from the chord from its start to its end); every letter lies wholly in the view; no letter's box (the text height or the letter's advance, whichever is more, plus the padding) meets the box of another label or symbol; and the same text is not already placed within 200 points (the several ways of one street, or the two carriageways of a divided road, carry the name once). The letters are laid out one by one at the advance given by Core Text for the whole text (`CTLineGetOffsetForStringIndex`, so kerning is kept), each turned to the line at its position and centred on it; the text reads left to right, upwards on a vertical line, so it is never upside down. A halo is drawn for all letters first, then the fills, so the halo of one letter does not cut into its neighbour. The names of borders are not written on the line: a `LabelStyle` with `placement: .besideLine` puts them beside it, at half the font size and 1 point from the middle of the line (close to the line, so the text may overlap the transparent band of a national border), and the standard style gives them a small font (national borders 5.5 points at zoom 6, 6.5 at 10, 7.5 at 14; state borders 5.5 at zoom 9, 6.5 at 14) and no halo. A name of two sides (`SidedName`) is split: the name of the region on the left of the line, looking along its points, goes above the line when the text reads along them and below it when the text reads against them (a line to the west, or a vertical one), so on a horizontal border the one region is above and the other below, each on its own side of the border, on a slanted or vertical one the sides are the two sides of the line in the same way. Both names are tried at the same place, centred on each other, and both must find room: if one does not, the stretch is tried at another place or the label is dropped. A name with no sides (see rule table 15) is written above the line. Cost, Halden (15 km store), 900 × 700 points at scale 2, draw with PNG encode: zoom 15 0.09 s to 0.12 s, zoom 17 0.06 s to 0.09 s with the labels on; the scene is unchanged. A name that is more than a few bends long or on a line that is never straight for its length is not drawn. In the standard style: major roads from zoom 12, streets from 15, service roads from 17, tracks from 15, paths from 16 (finer, brown and red-brown), rivers from 11, national borders from 6 and state borders from 9 (small, beside the border, in the colour of the border); the Watch style labels no lines. Limits: names run along one way, so a street made of many short ways with a gap in the straight part may get several labels spaced by the 200 point rule; map rotation (not implemented) needs the glyphs laid out again for the new angle and keeps them upright by the same rule.
- **Attribution (decided):** the scene carries the store file's `attribution` string and every backend draws it small in the bottom-right corner (`MapView` shows it as an overlay on the view), so no image derived from OSM data leaves without the ODbL credit. An empty string draws nothing. How it is shown is a style setting, `MapStyle.attribution` (`AttributionDisplay`): `full` (the whole string; the default and the `standard` style), `compact` (a short "© OSM" mark; the `watch` style, because the full text takes too much of a Watch screen) or `hidden`. With `compact` or `hidden` the app must make the full credit reachable elsewhere, for example in an About or Data screen, using `FeatureStoreFile.attribution`; exported images should use `full`. The OSM Foundation's guidelines accept a credit in a place users expect it (an About screen or a © control) for interactive maps, but this is not legal advice and stays on the release checklist (section 9). The CLI exposes it as `--attribution full|compact|none`.
- **PNG:** `pngData(for:style:scale:)` draws into an sRGB bitmap (scale 1 to 8, at most 16,384 px per side) and encodes with ImageIO. `geomapkit render` in `Tools/` uses it, and prints scene and draw times.
- **Measured (Mac, release, Liechtenstein 10 km store):** a 900 × 700 pt view at zoom 16 reads one cell and draws 3,003 features in 18 steps: scene 0.01 s, draw and PNG encode 0.09 s at scale 2. At zoom 13.5 (mid band, 12 cells, 6,225 features) 0.01 s and 0.07 s. These are Mac figures; the Watch cost is not measured.

### Map view (decided, `MapUI`)

- **`MapView`** takes a `FeatureStoreFile`, a `MapStyle` and bindings for the centre and the fractional zoom. The view owns the gestures and changes the bindings: drag to pan; pinch to zoom on iOS, iPadOS and macOS; the Digital Crown zooms on watchOS (drag pans there too). Zoom is limited to 2...20. On the Mac the scroll wheel zooms about the pointer (0.25 zoom levels per unit of wheel delta, a notch being about one unit; to be tuned with a real mouse, the coordinate under the pointer stays under it) and a two-finger scroll on a trackpad pans; the events come from a local `NSEvent` monitor (`ScrollWheelMonitor`) so the drag and pinch gestures are untouched, and the frame is redrawn 200 ms after the last event. Rotation: two-finger twist (`RotateGesture`, with pinch) turns the map about the view centre, a compass in the corner of a turned map resets it to north with a tap, and `MapView` has an initialiser with a `bearing` binding (the old one keeps north up). There is no rotation gesture on watchOS; an app may set the bearing (heading up).
- **Cached frame (battery rule).** The view draws a `MapFrame`: a `CGImage` of the viewport plus a margin of half the larger view side (at most 256 points) on every side, at the display scale (limited to 1...3). While the user pans or pinches, the frame is only moved and scaled (`MapFramePlan`), which costs nothing. A new frame is drawn when (a) the frame no longer covers the view, even during a gesture, (b) a gesture ends after the zoom changed, (c) the frame centre is more than half the margin off the view centre, even during a pan (drawing takes time, so the next frame must start before the edge shows; still one draw at a time), or (d) the style or store changes. There are no timers and no redraw on a schedule; the one delayed action is the 200 ms check for the end of a scroll on the Mac (not on watchOS).
- **Drawing is off the main thread** (`MapFrameRenderer`, a `Task.detached`) and one frame is drawn at a time; a request that arrives meanwhile replaces the waiting one, so work never queues. A stale frame (older style) is dropped and never shown. Errors (for example a store without a readable band) are shown as text when there is no frame.
- **Not done yet:** a cache of decoded cells across frames, rotating with a mouse (only the two-finger twist and the compass reset exist; Option-drag is a candidate), wheel and two-finger scrolling with a pointer on iPadOS, dark colours for the credit overlay (fixed dark text on a light box, right for the light standard style), fling/inertia after a pan, double-tap zoom, an energy measurement on a real Watch (the rule above is the design; the measurement is still needed), and a test app to try the view on a device. The view has tests for the frame plan and the model, but its gestures are not covered by automated tests.

## 5. Corridor (Watch data)

**The track is known beforehand (decided; v2, since v1 has no tracks).** For longer runs, ultras especially, the user has a track before the run: a GPX file, or a track created in an app that uses this package on macOS or iOS. The corridor is therefore cut from that track plus a buffer, before the run, on the phone or Mac; the phone does all the cutting and the Watch only asks for an area (see "Watch map data requests"). The v1 corridor holds map features only (the graph part below is v2). Open: runs without a track (question 42).

When a route is sent to the Watch:

- Take all edges within a buffer of the route polyline (starting guess 300 m to 1 km, configurable), plus the junction nodes they connect.
- Edges that cross the buffer boundary are clipped at the nearest node, and those nodes are marked as boundary nodes.
- The result is a few hundred KB at most and uses the same graph format as the regional graph, so the same router code runs on the Watch.
- Corridor features are cut from the regional feature store by spatial cell. Both files go over WatchConnectivity file transfer with the route.
- Edge attributes must be rich enough for all cost profiles (running, walking, cycling), since the Watch cannot fetch more.
- Access is sent as derived per-edge flags (can walk, can cycle, sidewalk beside the road), resolved on the phone from the raw tags; see "Access and sidewalks for routing" in section 2.

## 6. Off-route handling and rejoin

`RouteFollower` owns progress (distance along the route polyline) and off-route detection. Rejoin is a single multi-target search in `Router`:

1. Candidates are route nodes within a search radius, filtered by progress (see below).
2. Search from the runner outward and stop on any node in the target set.
3. Score each candidate as `cost(runner to rejoin point) + cost(remaining route from that point)`. Rejoining further ahead skips route, so the remaining cost drops and that candidate wins when the detour is cheap. Rejoining behind adds already-run route and is penalized or disallowed.

Who reroutes:

1. Phone reachable: ask the phone (full graph, full cost model).
2. Phone not reachable: run the search on the corridor graph.
3. Outside the corridor: no graph is available. Show a straight-line bearing and distance to the route, and say so in the UI.

A Watch reroute is marked provisional and reconciled when the phone is back.

Behaviour rules:

- Candidates use progress as well as proximity, so loops, self-crossings and out-and-back routes do not snap to the wrong pass.
- Hysteresis: require the off-route distance to exceed a threshold for several seconds, and do not replan again until the runner has moved some distance.
- Stability: stick with a chosen rejoin plan unless the runner clearly deviates from it.
- `RejoinPolicy` holds the tunables: search radius, backward allowance, skip limit, mandatory waypoints.

    - **J. The level builder (step 2, built, 2026-11-09).** `LevelBuilder.build(from: CellSource, spec: LevelSpec, tile:, margin:)` in `FeatureStoreBuilder` derives the file of one block of a level from the overview band of the source (a `StoreSet` or one file) and returns `nil` when the block has nothing to store. `LevelSpec(topZoom:classes:)` (top zoom 1 to 11) gives the storage zoom (top zoom + 2), the tolerance (0.5 pixel at the top zoom) and the minimum size (3 pixels); the caller passes the classes (the standard style's classes visible at the top zoom). The block is a tile whose zoom is at most the storage zoom of the level; the blocks of the levels are tiles of the zoom of the source blocks (8) or coarser, **not** min(storage zoom, 6) as change I said (a level block then lines up with the source blocks it is made from). It reads the source cells of the block and a margin of 32 cells around it (one source block, more than the 12 cells of the longest minimum size, at top zoom 3), so a line or area that crosses the border of the block is judged whole. *Lines:* the pieces are joined by end points (a piece that continues, ending exactly where a piece that has a predecessor starts), dropped if the bounding box is under three pixels, **cut at the border of the block first**, then simplified (end points kept) and cut into level cells with the clipper of the builder; the cut comes before the simplification because a block reads a chain that ends at its margin, and two blocks that simplified the chain they read would cross their common border at different points. The offset along the line restarts in every level block (a dash pattern restarts at the block border; the true start of a line is not known from a block). *Areas* (fill is even-odd, so a feature is a set of rings): the artificial edges between two cells that are both read are dropped, the real edges are chained end to start by exact coordinates, and an artificial edge on the border of the area that was read stays, because the feature continues there in a cell that is not read, and closes the chain; the rings are then filtered by size, clipped to the block, simplified (the real runs of edges only; the edges along the block border stay as they are and are marked artificial) and cut. A chain that does not close is closed with a straight line and its feature gets the `incomplete` flag (outline only, never filled), and it is counted in `LevelReport.openAreaChains`. *Known limits:* the artificial edges on the border of the whole source (the edge of the data) become ordinary edges of a level, so an area that is stroked would show a line there; the simplifier keeps the first vertex of a ring, which is a point on a cell border after a join (one extra vertex); a block reads at most 250,000 source cells with its margin (`LevelBuilder.maximumRegionCells`), larger blocks are refused, and the memory of the coarse levels (top zoom 3 to 5) is not measured. **Measured** on the block 8/140/75 (Stockholm, 99 MB) with top zoom 8 and the standard style's classes: reads 9,216 cells and 216,201 features, writes 4,179 features (the spike counted 3,953 without joining across the border of the block) in 16 level cells, 40,044 vertices, 302 kB, in 0.8 s (release, 9 source blocks opened); 1 open area chain, 24,498 lines joined, about 175,000 chains and rings dropped as small (numbers after the cut at the block: 4,172 features, 39,941 vertices, 301 kB). The east neighbour (8/141/75, a coast block) gives 1,140 features, 92 kB, 6 open area chains. **Seam between these two level blocks** (the points on their common border, by class and latitude): lines 43 on the left and 54 on the right, 42 the same; areas 114 and 110, 104 the same. So most features meet exactly, but not all; the unmatched points (about 2% of the left, 22% of the right for lines; 9% of the left for areas) are not explained yet (a feature that is small in one block and not in the other, or a chain that did not close, are the first suspects) and are to be looked at in step 4, together with the open chains along the seams of the source blocks (the sea of each source block is built alone and its outline at the seam may differ by a vertex, which the exact match does not accept). **A bug the first look found, and what it took to fix it.** With the levels of step 3 the sea east of Stockholm was missing at zoom 8: the level blocks of the open sea held sea pieces, but all marked `incomplete` (outline only, never filled). The area chains of the dissolve did not close, for two causes, found by printing the ends of the open chains. (1) *A neighbour cell counted as the twin of an edge when it only existed.* The dissolve dropped an artificial edge when the cell across it was present in the source, but a cell can be present and hold nothing of the feature: an open sea far from a coast has no `sea` piece in its block (the block 8/139/80 holds 28 objects and no sea; the blocks show it as a hole, as does the render of the blocks), and the sea next to it ended at an edge that was dropped. The edge is now dropped only when the cell across it holds a piece of the same feature, so the outline follows the edge of such a hole, as the blocks draw it. This fixed the seven blocks that were still incomplete after the first fix (138/79, 138/80, 139/79, 139/80, 143/65, 143/67, 145/65). (2) *Two blocks that simplified a coastline on their own.* Each base block simplifies the outline of the sea on its own, so where a coastline runs almost along the border of two blocks the two lines cross it at points that differ by kilometres (a few metres of difference, a shallow angle), and an exact join does not meet. An open end is therefore joined, nearest first, to a start within a pixel of the top zoom of the level, then to one on the same line of a cell border (a longitude or latitude that is the border of a cell of zoom 13, checked, not merely an equal number) within 16 cells, then to one on the same line at any distance, which also closes a ring along the edge of the data; the ring is cut at the block afterwards. Each join is counted (`LevelReport.joinedBySnap`, `joinedAlongBorder`) and `build-levels` prints the totals; a feature with more than 1,000 open chains is not joined (the pairs grow with the square; the joining takes the nearest pair first from a sorted list, once for each stage). Open sea in a block set (decided and built 2026-11-09). **Problem:** `prepareSea` builds the sea from the coastlines in a block's own cut, and returns nothing when the cut has none, so a block of open sea far from any coast got no `sea` feature (block 8/139/80, east of Bornholm, is a 128 kB file of borders and sea limits), and a block with nothing at all got no file (8/140/80, 8/139/81, 8/140/81); the render showed rectangular holes in the sea. Without a coastline in the block there is nothing to decide with. **Decision:** the producer decides after the blocks are built, from the neighbours (`OpenSea.fill`, called by `build-region`; the full profile only, because the Watch profile has no `coastline` class to tell "no coastline" from "no sea"). *Candidates* are the blocks that a source file covers at least in part (the tile itself, not the cut with its margin: `RegionIndex.regions(covering:)` over the tile, `coveredShare` above 0; a block no outline touches is unknown and stays empty). *Measured:* the outlines of the Geofabrik files stop at the territorial sea, so the open sea is mostly outside them (8/139/80 is 10% covered, 8/140/80 11%); requiring full coverage would have left exactly the holes this is about. The price is a block that straddles the edge of the data with land beyond it: it is filled only when every neighbour that has something to say shows sea, and a block next to a country that is not in the set is the case to watch and that have no file, or a file with no `sea` and no `coastline` feature. A connected group of candidates (4-neighbours) is all sea or all land, because a coastline anywhere in it would be in the cut of some block of it (the margin reaches 0.1° into the next block; a coastline way that crosses a block with no node in the cut would be missed, and shows up as a conflict). What its neighbours show decides: a neighbouring block (one with sea or a coastline) whose cells along the shared edge are **all sea squares** (one `sea` part that is exactly the cell square, overview band) says sea; one with **no sea in any of those cells** says land; anything else is unclear. The group is sea when every neighbour that has something to say says sea. A group that touches only land, only uncovered or unbuilt blocks or nothing, is left as it is; a group between sea and land (or with an unclear edge) is left and counted as *conflicting*, which points at a coastline that was not joined. **Writing:** a sea block is the cell square of class `sea` (the same part `SeaBuilder.wholeCell` gives) in all 1,024 cells and in **every band of the manifest**, not only the overview band: the reader takes the band from the manifest and not from the file (`ZoomBand.band(forZoom:available:)` over `StoreSet.bands`), so a file with one band would be empty at zoom 12 and above. A new file has the sources of the block's regions, so `build-region` finds it up to date next time; a sparse block that has a file is read and written again (`FeatureStoreFile.relations()` is new for this; names, tags and relations are copied to a new string table, the file keeps its name and sources) with the squares added, so what it had (borders, sea limits) stays. The manifest is written after each block, so a run that stops leaves a set that opens (a rewritten file always matches its entry); files are opened one at a time and not kept. A second run changes nothing, because the blocks have sea now. **Levels:** the pass does not remove the levels; `build-levels` compares the base blocks each level block came from (`derivedFrom`) with the manifest and finds the new and the changed ones, and the stale-level check at read time sees a changed size. **Cost:** an all-sea block is 3,072 small features, about 135 kB larger (8/140/80 went from 72 kB to 208 kB). The first run over an existing set cuts each empty block in the set's area once more (it has no entry yet), and then they have one. **Not done:** a sea block whose candidate neighbours are only diagonal; an open sea that no block with a coastline touches along an edge (a set of blocks that is all candidates); and the Watch profile. **Needs a rebuild or the extra pass:** a block set built before this change has the holes until `build-region` is run on it again (the existing blocks are up to date and stay as they are; only the pass runs, then `build-levels`).
